# The wasm fourth host — an executed-only column for the avatar

`ocaml/wasm/` is lane **L7** of `docs/research/2026-09-04-host-frontier-wasm-streams-promises.md`
(§4.3 "the spike", the lanes table row L7, ruling R1): compile the avatar with
**wasm_of_ocaml** and ask whether the result agrees, byte for byte, with the three hosts the
avatar is already required to agree on.

Answer, 2026-09-04, on this machine: **yes.** The witness report is byte-identical to the
committed three-host baseline (429 `HOLDS`, 0 `FAILS`, sha256 `9d59bcb4…`); the 158-program
corpus agrees with the committed faces on 158/158, and matches a same-pass js_of_ocaml face
byte for byte over the *whole* file on 158/158; and **no OCaml source line changed** — only
the dune stanza that selects the backend. The one thing that is genuinely different is the
integer width: wasm's `int` is **31 bits**, narrower than jsoo's 32 and native's 63 (§6.3).

---

## 1. The trust boundary

wasm is an **executed-only fourth host**, never a second modelled backend.

* The **modelled backend stays js_of_ocaml 5.7.1** under `--enable effects`
  (`ocaml/avatar/dune:46-47`), transcribed function by function in
  `src/OCaml5/Runtime/EffectJsoo.lean`. Nothing here changes that, and nothing here is modelled in
  Lean.
* This switch's js_of_ocaml is **6.4.1**, a different compiler with a different CPS pass
  (upstream `CHANGES.md`: 6.0.1 "dynamic switching between CPS and direct style"). So even
  the *jsoo* half of the `effect4-wasm` switch is not the modelled backend, and is not used
  as evidence about it.
* A wasm column that **agrees** is evidence of exactly the kind the other three columns are:
  the avatar's outputs are host-independent. A column that **disagrees** is a finding against
  `wasm_of_ocaml` or against the avatar's host assumptions — **never** a reason to change the
  Lean model, which is the authority (`ocaml/avatar/README.md` §"The Lean machine is the
  authority"). The modelled route (§4.2 of the note, three disciplines priced) opens only on
  a disagreement. There has been none.
* The pinned `effect4` switch is **not modified by anything in this directory**. Neither is
  anything under `ocaml/avatar/`: the avatar's sources are *copied* out of tree and the copy
  is rewritten (§5).

## 2. Layout

Build outputs live outside the repository, the precedent being `ocaml/link/README.md`
§"Layout" (`~/Dev/e4-link`): here it is `$E4_WASM_BUILD`, default `~/Dev/e4-wasm`.

| path | what |
| --- | --- |
| `tools/install-switch.sh` | creates (if absent) and populates the `effect4-wasm` opam switch; logs to `/tmp/e4-wasm-install.log` |
| `tools/build-wasm.sh [mode]` | copies the avatar's sources to `~/Dev/e4-wasm/avatar-<mode>`, rewrites the dune stanza (§5), runs `dune build --root .` |
| `tools/run-witnesses-wasm.ps1 [mode]` | runs `avatar_witnesses.bc.wasm.js` under the Windows node, writes `out/witnesses-wasm-<mode>.txt`, compares it with the committed baseline |
| `tools/run-corpus-wasm.ps1 [mode] [outdir]` | the 158 corpus programs through `avatar_main.bc.wasm.js`; the wasm twin of `ocaml/avatar/tools/run-corpus-jsoo.ps1`, line for line |
| `tools/compare-wasm.sh <a> <b> [sa] [sb]` | face-by-face comparison with the projection `ocaml/avatar/tools/compare-faces.sh` uses (event rows only) |
| `tools/compare-full.ps1 <a> <b>` | the same two directories compared whole, headers included — valid only between two faces produced in the same pass |
| `tools/probe.ml`, `tools/build-probe.sh`, `tools/run-probes.ps1` | the value profile (`Sys.int_size`, `max_int`, `Sys.word_size`, …) on native / bytecode / jsoo / wasm-cps / wasm-jspi — the `Backend.wasm` row `src/OCaml5/Runtime/Value.lean:49-58` is owed |
| `tools/measure.ps1` | the numbers of §7, into `out/measurements.tsv` |
| `out/` | GENERATED by the scripts above: `witnesses-wasm-cps.txt`, `corpus/wasm-cps/*.tsv` (158), `corpus/jsoo/*.tsv` (158, the same-pass comparison face), `probe.*.tsv`, `probe.*.err`, `measurements.tsv`. Regenerate, never hand-edit (`ocaml/STANDARDS.md` §3). |

Nothing in this directory is read by `ocaml/dune` — `ocaml/wasm/` is outside the workspace's
`(dirs …)`, exactly as `link/` is, because it belongs to a different opam switch.

**How the Windows node reaches a WSL build.** Unlike the jsoo face, which is one
self-contained `.bc.js`, the wasm face is a small loader plus a sibling `.assets/` directory
of `.wasm` modules that the loader reads relative to itself. The Windows `node.exe` loads it
straight off the UNC path `\\wsl.localhost\Ubuntu\home\kokok\Dev\e4-wasm\…` — no staging
copy to a Windows directory is needed, and the runners get that path from
`wsl -e wslpath -w`, the same trick `ocaml/avatar/run-witnesses.sh:54` uses.

## 4. Effect modes: which one, and why

`wasm_of_ocaml` compiles OCaml 5 effect handlers three ways
(`$(opam var --switch=effect4-wasm prefix)/doc/wasm_of_ocaml-compiler/README_wasm_of_ocaml.md`).
Measured on this machine's node:

| mode | builds? | runs on node v22.23.2? | evidence |
| --- | --- | --- | --- |
| `cps` | yes | **yes** — everything below is this column | `build-wasm.sh cps`, `run-witnesses-wasm.ps1 cps` |
| `jspi` (the compiler's **default**) | yes | **no** | `Fatal error: exception Failure("Effect handlers are not supported: the JavaScript Promise Integration API is not enabled")` — raised at the first `perform`, **with and without** `--experimental-wasm-jspi`. Upstream: JSPI "works by default in Chrome 137, Node.js 25, and higher". |
| `native` (WasmFX) | **no — the build refuses** | n/a | see below |

`--effects=native` is the one thing that refused. `wsl -e bash tools/build-probe.sh native
wasm-only` fails in `wasm-opt`, verbatim:

```
File ".js/effects=native/stdlib/_unknown_", line 1, characters 0-0:
Unknown option '--enable-stack-switching'
/home/kokok/.opam/effect4-wasm/bin/wasm_of_ocaml: Error: the following command terminated
unsuccessfully: wasm-opt -g --enable-stack-switching --enable-gc --enable-multivalue
--enable-exception-handling --enable-reference-types --enable-tail-call --enable-bulk-memory
--enable-nontrapping-float-to-int --enable-strings --enable-multimemory -O2
--skip-pass=inlining-optimizing --traps-never-happen …
```

and the same for `wasm-merge`. This is **binaryen**, not node: `wasm_of_ocaml` 6.4.1 asks
`wasm-opt` for the stack-switching feature and the installed **binaryen 120** does not have
that flag. So the WasmFX column needs a newer binaryen *before* it can even need the Node
canary that upstream names (`--experimental-wasm-wasmfx`, Chrome ≥ 148 or V8 ≥ 14.7.100).
The failure is at build time, is loud, and does not affect the `cps` column.

So `--effects=cps` is not a fallback here, it is **the only mode this machine can execute**,
and it is also the comparable column the note asked for (§4.3 step 3: "one column per effect
mode the runtime allows"). The flag does reach the compiler — the two modes produce different
artifacts (in the probe build, `stdlib-*.wasm` is 610,664 B under `cps` and 404,656 B under
`jspi`, the CPS transform being the difference), so the `jspi` refusal is the *runtime's*,
not a silent no-op. `wasm_of_ocaml --help=plain` lists `--effects=KIND` and no
`--target-env`, which is why row (c) of §5 drops the latter.

`node --v8-options` on v22.23.2 does list `--experimental-wasm-jspi` and
`--experimental-wasm-stack-switching`; the flag exists and the API behind it is not the one
`wasm_of_ocaml` 6.4.1 expects. The jspi column is therefore **owed to a node ≥ 25**, not
refused forever.

## 5. What changed for wasm

Every row is a rewrite of the **copy** under `~/Dev/e4-wasm/avatar-<mode>`, applied by
`tools/build-wasm.sh`. `ocaml/avatar/` is untouched.

| # | change | reason |
| --- | --- | --- |
| a | `(lang dune 3.0)` → `(lang dune 3.17)` in `dune-project` | dune's `(modes wasm)` and `(wasm_of_ocaml …)` fields are 3.17+; the avatar's own project declares 3.0 (`ocaml/avatar/dune-project:1`) and the note flagged the bump as "to be checked". Nothing else in the avatar's dune file depends on the language version. |
| b | `(modes byte exe js)` → `(modes wasm)` | select the wasm face for `avatar_main` and `avatar_witnesses`. |
| c | `(js_of_ocaml (flags (--enable effects --target-env=nodejs)))` → `(wasm_of_ocaml (flags (--effects=cps)))` | 6.x spells the effect implementation as a mode, not a switch (`--enable effects` no longer exists); `wasm_of_ocaml --help=plain` has no `--target-env` at all — the generated loader detects node by itself, and does so correctly (§6). |
| d | the build is out of tree, from copied sources | the `effect4-wasm` switch must not write into `ocaml/_build` (owned by the `effect4` switch) and must not modify the avatar. Precedent: `ocaml/link/README.md` §"Layout". |
| e | `jsprobe.ml` and `fuzz_register.ml` are not copied | they are outside the avatar's dune stanzas already (`ocaml/avatar/dune:7-9`): `jsprobe` needs its own js runtime file and `-no-check-prims`, `fuzz_register` links a generated fixture. Neither is part of the witness or corpus faces. |
| f | **nothing else** | no `.ml` file was edited, no library was dropped, no primitive was stubbed. The avatar names no `Unix`, `Domain` or `Thread` (checked by grep over `ocaml/avatar/*.ml`); its only host surface is `Sys.getenv_opt` and `Printexc.to_string`, both of which wasm_of_ocaml supports. `corpus_data.ml` is generated by the same dune rule as in the avatar, so the corpus is compiled in and there is still no file to open. |

The build refused nothing **in the `cps` column**: no library, no primitive, no external.
There is no "libraries that would not build" row and no adaptation row beyond (a)–(e). The
only refusal anywhere in this lane is `--effects=native`'s `wasm-opt` flag (§4), which is a
toolchain version, not an avatar adaptation.

### 6.3 The value profile — the one real difference

```powershell
wsl -e bash ocaml/wasm/tools/build-probe.sh cps
wsl -e bash ocaml/wasm/tools/build-probe.sh jspi wasm-only
pwsh ocaml/wasm/tools/run-probes.ps1
```

`src/OCaml5/Runtime/Value.lean:49-58` records `Backend | native | jsoo` with `intBits` 63/32. The
wasm row is now measured, and it is **neither**:

| fact | native | bytecode | jsoo 5.7.1 | **wasm 6.4.1** |
| --- | --- | --- | --- | --- |
| `Sys.backend_type` | `Native` | `Bytecode` | `Other js_of_ocaml` | `Other wasm_of_ocaml` |
| `Sys.int_size` | 63 | 63 | 32 | **31** |
| `Sys.word_size` | 64 | 64 | 32 | 32 |
| `max_int` | 4611686018427387903 | idem | 2147483647 | **1073741823** |
| `min_int` | −4611686018427387904 | idem | −2147483648 | **−1073741824** |
| `Sys.max_string_length` | 144115188075855863 | idem | 2147483643 | **1073741819** |
| `Sys.max_array_length` | 18014398509481983 | idem | 536870911 | **268435455** |
| `1 lsl 62` | −4611686018427387904 | idem | 1073741824 | **−1073741824** |
| `int_of_float 1e18` | 1000000000000000000 | idem | −2147483648 | **−1** |
| `Sys.big_endian`, `compare`, float printing, one performed-and-resumed effect | agree on all four hosts | | | |

**31-bit integers.** wasm_of_ocaml represents OCaml `int` as the Wasm GC `i31ref`, so the
wasm host's `int` is *one bit narrower than jsoo's and 32 bits narrower than native's*. The
estate encodes `Nat` as `int` in places (`ocaml/gen/NOTES.md` "`Nat → int`"), and the note
listed this as unmeasured (§8.2). It is now measured, and it is a **new refusal row**: any
value crossing the wasm boundary must fit in 30 bits plus sign. The avatar never noticed —
its counters, fiber ids, tokens and op budgets are far below 2^30 — but a `Backend.wasm` row
with `intBits := 31` is owed in `Value.lean` before anything is claimed about wasm values.

Reading: on this workload wasm-cps and jsoo are close — wasm is 5% slower on the witness
report (264 ms vs 252 ms) and 14% slower over the corpus (37.4 s vs 32.7 s, i.e. 237 ms vs
207 ms per program) — and both are dominated by node process startup, which the native
column (2.0 s for the same 158 programs, ~13 ms each) makes obvious. These are **not** effect
performance numbers: upstream says `cps` performs effects faster than `jspi`, and no
per-effect benchmark was run. The size result is the striking one: **the wasm code is
about 3.3× smaller than the equivalent JavaScript** (1.41 MB of `.wasm` against 4.63 MB of
`.bc.js`), and the loader is 45 KB. Under `--effects=jspi` the `stdlib` module alone drops
from 610,664 B to 404,656 B, so the executable column would shrink further on a node ≥ 25.

`stat`/`du` inside WSL and the times from `System.Diagnostics.Stopwatch` around the same
process invocations the corpus and witness runners use.

## 9. What a fifth step would be

In the order that buys the most per hour:

1. **`Backend.wasm` in `src/OCaml5/Runtime/Value.lean`** with `intBits := 31`, cited to
   `out/probe.wasm-cps.tsv`, plus the refusal row "an `int` crossing the wasm boundary is
   30 bits plus sign". Small, and it is the one place this spike changes a Lean claim (a new
   host row, not a model change).
2. **A node ≥ 25 in WSL or on Windows**, then `run-witnesses-wasm.ps1 jspi` and
   `run-corpus-wasm.ps1 jspi`. Agreement *across effect modes* is a stronger result than a
   fourth host: the avatar's witnesses claim independence from the effect implementation, and
   `cps` + `jspi` + native OCaml 5 + `effect.js` is four implementations of one test. `jspi`
   is also the mode where §2 of the note stops being an analogy — a `perform` is a stack
   suspension into a JS promise, so `Promise.lean`'s `awaitK`/`resumeK` *is* the runtime.
3. **The fourth column in the estate's own scripts** — `avatar/run-witnesses.sh` and the
   corpus runners grow a wasm row, guarded by "the `effect4-wasm` switch exists". That is the
   recurring cost the note priced (§4.2, "the fourth column in three scripts"); until it is
   paid, this directory is the only thing that runs the column.
4. **The daemon's four externals as wasm imports** (§8 row 1), which is what makes a wasm
   *service* possible rather than a wasm *executable*.
5. **`--effects=native` (WasmFX)**, which needs a binaryen new enough to accept
   `--enable-stack-switching` *and* a Node canary. It is the mode closest to OCaml 5's own
   `fiber.c` and therefore to `src/OCaml5/Runtime/Effect.lean`'s 65 arms — the only one of the three
   where a future modelled backend would reuse the native machine rather than the CPS pass.
