# The extern table of the engine seam — ocaml/engine/api_engine.ml
# (docs/research/2026-09-08-engine-a1-state.md §1.4; the row format is the docstring of
#  src/OCaml5/Lcnf/Externs.lean).  Regenerate with ocaml/engine/tools/gen-check.sh.
#
# A `field`/`type` row changes a TYPE, so every generated site that still treats the carrier
# as a list is an ocamlopt type error: the table is complete iff api_engine.ml compiles, and
# it compiles as a functor body with no instance (engine-a1 §1.3).
#
# DEVIATIONS from engine-a1 §1.4/§1.5, recorded here because lane C implements against them:
#   D1  The dispatcher is A3's whole-dispatcher carrier (`e4_buckets.mli`, engine-a3 §1.1.1),
#       not a TABLE of buckets holding a FIFO.  So `Effect4.Machine.Dispatcher` is an extern
#       TYPE (`(…) task D.t`), `Effect4.Machine.Bucket` and the FIFO functor parameter are
#       gone, and `Dispatcher.insert` is never reached.  The functor is
#       `Make (M : TABLE) (T : TRACE) (L : LAYERS) (D : DISPATCHER)`.
#   D2  TABLE/TRACE/LAYERS are emitted as A1 §1.5 prints them, byte for byte; DISPATCHER is
#       e4_buckets.mli's own signature, so `module D = E4_buckets` needs no adapter.
#   D3  Every `[carrier]` row of A1 §1.4 is a `[hand]` row here.  A1 aimed them at concrete
#       modules (`E4_fibers.update`, `E4_store.peek`, `E4_memo.entry_at`); a concrete module
#       cannot have `'a M.t` for an abstract `M`, so the functor body would not type-check on
#       its own — and that type-check IS the completeness proof.  Every row therefore goes
#       through the functor parameters, and every one of them also projects a generated
#       record field, so all of them live in the prelude
#       (ocaml/engine/tools/api_engine_prelude.ml).  `e4_shim.{ml,mli}` is not created: a
#       separate compilation unit cannot see the record types, which are inside the functor.
#   D4  A1's rows for `refPeek`/`refPoke`/`Dispatcher.insert`/`ScopeStore.entryAt` are not
#       here: each is inlined or reached only through a row that deletes it, so a row would be
#       a stale ledger and the generator refuses one (G10).
#   D5  Two constructor rows (`Dispatcher.mk`, `MemoMap.mk`) that A1 does not have: the mono
#       phase inlines `⟨[], false⟩` into `fireState` and `⟨…, parent, []⟩` into `syncOpStep`,
#       both of which must stay generated.
#   D6  Q6 (`Nat.div`/`Nat.mod` by zero) is two `fn?` rows: the current root set never reaches
#       division, so a mandatory row would fail G10.  They fire the moment one does.
#   D7  (lane G2) `Point.path` and `Point.env` are carriers too, and they are the ones the
#       run time was in (docs/research/2026-09-08-engine-prof-chain.md: 98.5 % of the
#       retained machine, 58 % of the time).  Two mechanisms carry them that the other rows
#       do not need: the chain's `@node` token, because the path carries the NODE it
#       addresses and `node` is declared inside the functor; and the `ops`/`carg` rows,
#       because `p.path ++ [i]` is written INLINE in nine declarations that must stay
#       generated, so no `fn` row can reach it.  The functor gains `(P : PPATH) (E : PENV)`.
#   D8  (lane G3) `RunMachine.fibers` is NOT a `TABLE` any more: it is `FIBERS`, a table that
#       also MAINTAINS the completed view, because `RunMachine.completedExits` (Fibers.lean:
#       1543) is a Theta(N) filterMap called on essentially every step -- 62.7 % inclusive on
#       fan-out 512 after G2, and NOT cacheable (G2 measured the memo at 0.0 % hits).  The row
#       needs the EXIT type as a second carrier argument, which is what the `+` chain token
#       spells: `+exit_:2,3,4,5,6` is `exit_` applied to arguments 2..6 of the field's element
#       type `(nu,s,b,e,d,i,a,ch,k,f) run_fiber`, i.e. `(b,e,d,i,a) exit_`.  The functor gains
#       `(F : FIBERS)`, and the fiber table's five writes take `~exit_of` in the prelude.

# ---- G2: the carrier operations of the path and the environment ---------------------------
# An `ops` row is the OCaml form of ONE list operation applied to a value of the carrier whose
# chain ends in the key.  It is what reaches the inline sites a `fn` row cannot: `path ++ [i]`
# is `P.snoc`, `path ++ pc` is `P.append`, `env[i]?` is `E.get`, `List.length env` is
# `E.length`, `List.take` (as the mono phase writes it, `takeTR.go env env n []`) is `E.take`.
# `P.snoc`/`P.append` take `Node.child` because the node rides along and `node` — with
# `program_node_child` — is generated BELOW this prelude, so the row hands it in at the call
# site (the same mechanism as `sh_api_load`; `emit` adds the emission-order edge).
ops P.t snoc P.snoc program_node_child
ops P.t append P.append program_node_child
ops P.t to_list P.to_list
ops E.t snoc E.snoc
ops E.t append E.append
ops E.t get E.get
ops E.t length E.length
ops E.t take E.take

# `Node.at_` is answered by the path itself.  The row's hand body compares the node the caller
# passes with the one the spine was built from and reads the carried node when they are the
# same, and WALKS otherwise — so `sh_node_at c n p = Node.at_ n (P.to_list p)` for every n and
# p, with no assumption about the caller (law NODE-AT).
fn Effect4.Program.Node.at_ 2 sh_node_at program_node_child
