# link/ report — the daemon core over the route-1 bridge (2026-09-04)

`ocaml/link/` is now a standalone dune project: a library `effect4_bridge`
(ten components, one per file, a property list at the head of each), three thin drivers
(demo, bench, probe), one test executable (24 checks, all green), and the scripts that
compile `Bridge.lean` and generate the link flags. It implements §1–§4 of
`docs/research/2026-09-04-effect-native-daemon-architecture.md` minus checkpoint, store
and migration: mailbox, worker, router, ring, host, and the typed bridge under them.
Every number below comes from a command listed in §5; the outputs are verbatim.

## 3. The memory rule, as built

A machine's `lean_object*` lives in the worker's private table on its domain: `Load`
creates it there, `apply` replaces it with the stepped value and releases the old one
immediately (`E4_bridge.release` → `lean_dec` on the owner), `Shutdown` releases whatever
is left and calls `lean_finalize_thread`. Nothing that crosses a domain holds a session:
the router's table has the mailbox only; `Inspect` replies with a status record of ints,
strings and parsed fiber lines; event rows are strings in the ring. `Domain.spawn` gives
each worker its own OS thread, and `lean_initialize_thread` (exported by `libleanrt.a`,
declared by hand since `lean.h` does not) gives it its own Lean heap — the 1/2/4/8-domain
bench and the two-domain demo run on exactly this, with no `lean_mark_mt` anywhere.

## 4. Deviations from the brief, and why

- The link flags are `link_flags` on the executables and the test, as the brief said, as
  `-cclib` pairs. The first attempt put them on the library (`c_library_flags`) so every
  dependant inherits them; dune then also feeds them to the bytecode stubs `.so`, and
  `libleanrt.a`'s local-exec TLS (`g_finalizers`) cannot be linked into a shared object.
  ocamlopt orders command-line `-cclib` objects after the library's stubs archive, so the
  static resolution order is right; the archives sit in one `--start-group` anyway.
- Four components beyond the six named: `e4_inbox` (a worker owning many machines needs
  one run queue, not one condition per mailbox), `e4_reply` (the inspect channel),
  `e4_quiescence` (the counter behind `run_until_quiescent`), `e4_snapshot` (the oracle
  behind B5 — also the fallback the brief asked for if an export had been missing; none
  was, so it is only an oracle).
- `send` has one more refusal than `[`Full | `Unknown]`: `` `Stopped `` after `shutdown`.
  `spawn` raises `Invalid_argument` for a program the Lean table lacks (R3).
- The `.sexp` files are generated into the source directory with a `GENERATED … do not
  edit` comment (dune accepts `;` comments in `:include` files — checked) and absolute
  paths; they are per machine, never shared.
- Sequence numbers are stamped under the mailbox lock (M5), not under one global lock:
  per machine FIFO order equals seq order, across machines the seq is one total order
  every machine respects — the merged log is a linearization. The demo's seq 4 in (b) is
  B's rule-queued `fire:0`, applied after `flush` had already drained the dispatcher: a
  step that emits no row leaves no line in the log.

## 8. Not done, and why

- Checkpoint, store writer, migration (architecture §4 rows 5–7): out of this brief; the
  ring is in memory only and there is no wire — the drivers are the callers.
- A host-level `Full` refusal test: not deterministic without a way to hold a worker
  still; M2 is tested at the mailbox, and the host path returns the same `Error `Full`.
- The bytecode stubs `.so` is still produced by dune (unused; it links with unresolved
  Lean symbols, which a shared object allows) — harmless, not suppressed.
- `wait_zero_for` polls at 0.2 ms because the standard library's `Condition` has no
  timed wait; the untimed `wait_zero` is what the bench uses.
- The snapshot-text fallback the brief asked for "if an export is still missing" was not
  needed: all five exports and `pAwait` were in `Bridge.lean` and in the compiled
  `Bridge.o` at the first build. `E4_snapshot` remains as the oracle of B5.

## 9.2 The bytes path: three stubs, one typed face, five checks

Read off `src/OCaml5/Bridge.lean` (not changed by this lane):

    e4_name       : Session → String        -- the table name, `bytes`, or `!refused:<reason>`
    e4_program_hex: String → String         -- canonical bytes as hex, "" for an unknown name
    e4_load_hex   : String → UInt32 → Session  -- hex → bytes → decode → wellTyped → load

`e4_load_hex` is **total**: every string answers a `Session`. Bytes it will not run come
back named `!refused:decode` or `!refused:ill-typed`, carrying **p42's machine** — so a
caller that stepped a refused session would silently run `p42` in place of the bytes it
asked for. That is the shape the OCaml face has to close.

- `e4_stubs.c:56-60` declares the three; `e4_stubs.c:215` is `caml_e4_name` through the
  existing `E4_STRING_PROJECTION` macro (inc, call in the blocking section, copy out, dec);
  `e4_stubs.c:252-280` are `caml_e4_program_hex` and `caml_e4_load_hex`, shaped like
  `caml_e4_load` — the argument copied to a C buffer first, `lean_mk_string` and the call
  inside `caml_enter/leave_blocking_section`, the result boxed or copied after (C1, C3),
  the session released like any other (C2). New property row **C6** (`e4_stubs.c:28-33`):
  the bytes path crosses as text only, and the C face does not read the refusal name —
  turning it into an error is the OCaml face's job.
- `e4_bridge.ml:50` `type refusal = Decode | Ill_typed | Other of string`;
  `e4_bridge.ml:67-69` the three externals (`name`, `load_hex_raw`, `program_hex_raw`);
  `e4_bridge.ml:120-149` the face:

      val name        : t -> string
      val program_hex : string -> string option                     (* None for Lean's "" *)
      val load_hex    : hex:string -> fuel:int -> (t, refusal) result

  `load_hex` reads the name, and on `!refused:<reason>` **releases the session** and
  answers `Error`; `Ok` is the only way a session escapes, so refused bytes cannot be
  stepped. New property row **B7** (`e4_bridge.ml:24-33`).
- `e4_test.ml:278-475` the checks. `bridge-name` (a step keeps the name; `program_hex` is
  `None` for `nope` and `""`; a released session's `name` raises), `bridge-hex-roundtrip`
  (every program of the table: `load_hex (program_hex p)` stepped evaluate + flush has the
  same snapshot text, armed, finished, trace_len, fibers and events as `load p` stepped the
  same way — the snapshot compared with its `machine <name>` head removed, since the two
  sessions are named `p` and `bytes`), `bridge-hex-refuses`, `bridge-hex-ill-typed` and
  `bridge-hex-tamper` (below). 24 checks → **29**, all green.

## 9.3 What tampering answers

`bridge-hex-refuses` — eight tampered forms of `pFork`'s 290 canonical bytes, each
`Error Decode`: empty, odd-length hex, a non-hex digit, the first byte flipped, one byte
truncated, half the payload truncated, one trailing byte, and the program twice. Then the
same input through the raw external, to show what the typed face is protecting against:
`e4_load_hex (hex ^ "00")` answers a session **named** `!refused:decode` whose machine,
stepped evaluate + flush, has exactly `p42`'s snapshot body — a repair, if it ever escaped.

`bridge-hex-ill-typed` — the two refusals are distinguishable. `pBind`'s bytes contain the
sub-frame of its second `Eff`, `succeed (app "succ" [var 0])`, a program with a free
variable; the test walks the framing (`tag :: be64 length :: payload`) to carve it out.
It decodes exactly, and `wellTyped` is what refuses it: `Error Ill_typed`.

`bridge-hex-tamper` — every single byte of every program of the table, flipped
(`b lxor 0xff`), loaded, and (when it loads) stepped evaluate + flush; a survivor's fiber
exits are printed with it, so what the byte became is on the record. Verbatim from the run
below:

```
     p42     66 bytes flipped:  65 refused, 1 another program at 65 [success:nat 213], 0 silently the same
     pBind  199 bytes flipped: 198 refused, 1 another program at 84 [success:nat 255], 0 silently the same
     pFork  290 bytes flipped: 289 refused, 1 another program at 168 [success:value/success:nat 248], 0 silently the same

```

1315 single-byte flips, 1310 refused, 5 decoded to a different program, **0** silently the
same program. The five survivors are exactly the digit bytes of the literals — a `Nat` is
base-256 big-endian with no leading zero byte and `0` is the empty digit string
(`Effect4.Store.Canonical.natBytes`), so each of these five small literals is one byte and
its flip is another valid digit — and the exits say so: `p42`'s byte 65 is the digit of
`nat 42` and the run exits `nat 213` = 42 xor 0xff;
`pBind`'s 84 is the `nat 1`, and `succ 254` exits `nat 255`; `pFork`'s 168 is its child's
`nat 7`, which exits `nat 248`; `pTwo`'s 168 and 394 are its `nat 1` and `nat 2`, exiting
`nat 254` and `nat 253`. Every other byte is framing — a tag, one of the eight big-endian
length bytes, or a constructor index — and every flip of one is refused. `pAwait` has no
literal digit at all (`lit unit` and the de Bruijn `var 0` are zero-digit `Nat` frames), so
all 159 of its bytes are framing. The check asserts the property, not the counts: no flip
is ever silently the same program.

## 9.5 Not done, in this pass

- No Lean-side change was needed and none was made: the three exports were already in
  `src/OCaml5/Bridge.lean` and in the compiled `Bridge.o`, so nothing is owed to the
  coordinator from this lane.
- There is no `program_bytes` for a program the table lacks: `program_hex` only answers for
  the five names, since only Lean can encode. Authoring bytes outside Lean — the point of
  `load_hex` — waits for the OCaml encoder (`ocaml/eff`) to be wired to this face; when it
  is, `bridge-hex-roundtrip` becomes a differential of the two encoders.
- `Other of string` in `refusal` is unreachable from today's `Bridge.lean` (its only names
  are `decode` and `ill-typed`) and untested. It is there so a reason added on the Lean
  side arrives as data rather than as a session handed out by mistake.
- The tamper sweep is single-byte only; two-byte flips and reordered frames are not swept.
- The three drivers do not touch the bytes path: `e4_demo`, `e4_bench` and `e4_probe` all
  load by name (`E4_bridge.load`), so `program_hex` / `load_hex` / `name` are exercised by
  `e4_test.exe` alone. A driver that loads a machine from bytes is worth having when the
  OCaml encoder arrives; it would have nothing to encode today.
- There is no `.mli` for `E4_bridge`, here or anywhere in the library, so `load_hex_raw`
  and the other externals are reachable beside the typed face — `e4_test.ml:404` uses that
  deliberately, to show what the face is protecting against. Sealing the interface would
  make B7 hold by construction rather than by convention; not done in this pass.
