# The OCaml estate

OCaml is the primary host of the Effect model (ruling of 2026-09-04, `docs/research/
2026-09-04-ocaml-estate-and-parity.md`). This directory is one dune workspace holding every
OCaml program of the estate; its Lean half is the lake library `OCaml5` under `src/OCaml5/`
(root module `src/OCaml5.lean`). Nothing here is a spike any more: each project is a library
with thin drivers, one component per file with a property list at its head, generated files
marked and regenerable, and a report behind every number (`STANDARDS.md`).

Two runtimes exist on purpose (`2026-09-04-ocaml-estate-and-parity.md` §4f–§4g):

* **the visible machine** — the Lean `RunMachine` itself, running in OCaml. Route 1
  (`link/`) holds the compiled Lean machine as an opaque value and steps it; route 2
  (`gen/`) is Lean's own compiler IR translated into typed OCaml. Every fiber, frame,
  park token, pending resume and event is a field of one value, so it can be inspected,
  serialised, moved between domains and messaged through the model's own decision
  alphabet. Fidelity is the compiler's.
* **the avatar** — the same machine as OCaml 5 effect handlers (`avatar/`), with the
  frame stack on the OCaml stack. It is fast and effects-native, and by construction never
  one-for-one; the corpus differential against rc.112 and the witness report are its
  evidence, and the relation to the Lean machine (A3) is its owed theorem.

The daemon (`server/`) serves the avatar over JSON lines on three hosts; `eff/` is the
Lean program IR `Eff` as an OCaml language, so OCaml can author programs the Lean machine
decodes exactly.

## The fidelity ladder

Highest fidelity first (`2026-09-04-ocaml-estate-and-parity.md` §4f):

1. compiled Lean linked into the OCaml process — `link/` (native only; the boundary is
   `e4_stubs.c`, a stated trust boundary, not model code);
2. Lean's compiler IR translated to OCaml — `gen/` (all three hosts, typed, value-threaded,
   no handlers; fidelity = the compiler's minus a small rule table);
3. a syntax-level transpiler — `src/OCaml5/Transpile.lean` (readable, re-does elaboration
   decisions);
4. a hand port with descriptions and an overlay — `avatar/` (the right mechanism only where
   representation differs on purpose).

## Building

The switch is `opam switch effect4`: OCaml 5.1.1, dune 3.24, js_of_ocaml 5.7.1 pinned (the
modelled backend), the Jane Street v0.16 set; the pins are in `avatar/effect4-avatar.opam`.
On the PC the switch lives in WSL Ubuntu and every command below runs there:

```bash
eval $(opam env --switch=effect4 --set-switch)
cd /mnt/c/Users/kokok/Dev/lean4-effect4/ocaml
dune build            # avatar, server, gen (and eff once its line is in ./dune)
dune test
```

Node is the Windows one (`node.exe`, reachable from WSL through interop); the scripts under
`avatar/tools/`, `server/tools/` and `link/tools/` know this. `link/` is built by
`link/tools/build.sh`, which first compiles `src/OCaml5/Bridge.lean` against a Linux
`lake build Effect4:static` tree and generates the per-machine link flags
(`link/c_flags.sexp`, `link/lean_flags.sexp`, ignored by git). The Lean half is
`lake build OCaml5` from the repository root.
