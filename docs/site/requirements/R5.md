# Requirement R5: Services and layer provision

This page explains requirement R5 in Effect4. It covers what the requirement asks for service tables and layers, why static requirement grading matters, and how the property is checked.

## What the requirement asks {#what-it-asks}

Requirement R5 demands that services are managed through static service tables in the application typing signature and discharged by layers (`docs/core/system-map.md` §8):
- Service tables: service keys and types form an explicit static component of Σ_app.
- Value typing: constructed layer values must fit their declared service keys.
- Flat coeffect grading: requirement rows grade programs by the service keys they need for execution.
- Capability discharge: providing a layer discharges its output requirement keys.

A program with an unfilled service requirement must not execute at the top level.

## Why it matters {#why-it-matters}

Enterprise applications structure dependencies using modular layers that construct database clients, loggers, and authentication handlers.

If requirement rows were untracked, a program could fail at runtime with missing service defects deep inside execution.

Grading a program by its requirement row lets the checker refuse a missing service before the run begins.

## How it is checked {#how-it-is-checked}

The requirement is checked by proving layer construction, requirement discharge, and context algebra theorems:
- Totality of layer building under satisfying contexts is stated by `build_total` (`src/Effect4/Laws/Program/BuildTotal.lean`).
- Capability discharge under layer provision is stated by `provide_discharges` (`src/Effect4/Program/Provision.lean`).
- Closure of layer composition is stated by `provide_closed` in the same file.
- Commutativity of row merging is stated by `merge_rows_comm` in the same file.

The plan on this page gives each theorem's status and the goals it rests on.
