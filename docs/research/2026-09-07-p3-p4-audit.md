## Finding 1: repeated scope registration leaks a child (required C1 repair)

`Program/Compile.lean` supplies `p.fuel` as the scope-finalizer key in
`actionAt` (`forkIn`, `runIn`) and `forkScopedAt`. Re-executing one point in a
loop repeats that key. `Machine/Scope.lean`'s `tableInsert` correctly replaces
an existing equal key, so the second registration removes the first child's
cleanup obligation. `Machine.linkScope` also gives that same key to each
observer. The pinned source allocates a fresh object each time at
`internal/effect.ts:5366-5372` and `5457-5460`.

The audit runs a well-typed, printable scoped loop which forks children
waiting on one uncompleted Deferred. The command tape is `[evaluate, flush]`,
compile fuel 40, command fuel 400, scheduler budget 2048. The actual printer's
expression is executed unchanged on pinned rc.112 with the existing bounded
host observer (32 callback rounds).

| Iterations | Lean frame: finished root/children | Lean term | Effect host | Command fuel sufficient |
| --- | --- | --- | --- | --- |
| 1 | `[true, true]` | `[true, true]` | `[true, true]` | yes |
| 2 | `[true, false, true]` | `[true, false, true]` | `[true, true, true]` | yes |

The host children finish with interruption. This is a source discrepancy on
an admitted composition, not insufficient fuel. Both Lean machines agree,
so it does not refute P3. The key scheme predates Fable for forkIn/runIn;
Fable's forkScoped wrapper reuses it. It is not attributed solely to this
delivery as a new regression.

The review retains `E4-CHECK-CE-016` in the register and the finite failing
expectation plus positive control in `SimulationContract`. Passing that
battery records the current defect, not its repair. The reviewed
[registration brief](2026-09-07-scope-registration-repair.md) names the runtime
allocation and proof obligations. Excluding repeated loops would violate the
unchanged arbitrary-composition goal.
