# Decision 12: every boundary value carries an Effect Schema

Date: 2026-09-10. The owner's addition to the eleven boundary decisions
(`2026-09-10-boundary-decisions.md` §5), verbatim: "an Effect Schema representation of all
boundaries. The program at its most degenerate still emits an Effect Schema representation of
whatever value is there. This way, serialized to Effect TypeScript or not, we can always say
what type it may emit, either as a plain object from the encoded value or as an effect. Enforced
for all Eff programs. Higher-order schema-native typings and utils; canonical schemas for row
types."

This also answers DI-08 ("is Schema in the release?"): the persisted data plane is in, as the
language every boundary is described in. The authoring plane stays archive-tier per the docs
scout (`2026-09-10-v0-scout-docs.md` §3).

## 1. The decision, precisely

Every `Ty` has a Schema representation. Every `EffTy` has a Schema document: the answer, the
error, the requirement row, and the exit that unites them. Every well-typed `Eff` program
therefore has a document, computed, never authored; `Api.typeOf` and `Api.schemaOf` answer
together or refuse together. The printer emits the document beside the program, so a printed
module carries both its `Effect.Effect<A, E, R>` annotation and the `Schema.Exit(…)` that
describes what running it produces. A machine value at a boundary encodes to JSON under the
column's representation and decodes back, with the laws that say so. The truth harness checks
the recorded exit of every corpus program against the program's own schema on rc.112.

That is the sentence "we can always say what type it may emit, as a plain object or as an
effect", made into four functions and two gates.

## 3. What is missing, in the order it is built

### S-1. `Ty.schema : Ty → Representation`

The fifteen constructors, sixteen with `lit`, each to the representation rc.112 would give
the rendered type. `handle target` and `fiberOf` are the "most degenerate" cases: a handle
is opaque on the host, so its representation is a `declaration` with no encoding, named by
its target spelling, which is exactly what `Schema.declare` produces, and a fiber is the same.
Everything else encodes.

| `Ty` | representation | note |
| --- | --- | --- |
| `never` | `never` | |
| `unit` | `void` | |
| `nat` | `number` with `Check.int` and non-negative | `int` the same, until T5's float carrier |
| `string`, `bool` | `string`, `boolean` | |
| `lit s` (S4b) | `literal (string s)` | the S4b arm |
| `option t` | `declaration` for `Schema.Option` with `[schema t]` | rc.112 `Schema.ts:9686` |
| `list t` | `arrays` of `schema t` | |
| `prod a b` | `tuple [a, b]` | the DB-15 pair |
| `except e a` | `declaration` for `Schema.Result` with `[a, e]` | `:10007` |
| `exitOf a e` | `declaration` for `Schema.Exit` with `[a, e, Defect]` | `:10906`, `:10844` |
| `causeOf e` | `declaration` for `Schema.Cause` with `[e, Defect]` | `:10568` |
| `fiberOf a e` | `declaration`, opaque, identifier `Fiber.Fiber<a, e>` | no encoding, by design |
| `handle target` | `declaration`, opaque, identifier `target` | no encoding, by design |
| `union a b` | `union` of the members' schemas, `anyOf` | after `normalize` |

`schema` is stated on normalized types: `schema t = schema t.normalize`, so the S4a
canonical API and the document agree, and the T3 canonical column (a union of per-tag pairs)
has one document. A day.

### S-2. `EffTy.document` and `Row.document`

An `EffTy` becomes a `Document` whose root is the exit schema, `Schema.Exit(answer, error,
Defect)`, and whose references table names the answer and error schemas and one entry per
requirement key. That is the "as an effect" reading. The "as a plain object" reading is the
answer's schema alone. `Row.document` does the same for a row's request, answer and error.

The canonical row schemas the owner asked for live here: `sqlRows`, `sqlError`, `kvError`,
the `strings` parameter list, one named reference each in the references table, generated
from the package tables, never hand-written. A package's document is the set of its rows'
documents under one references table. A day.

### S-3. `encode` and `decode` at a type, with laws

`Ty.encode : (t : Ty) → Val → Option Json` and `Ty.decode : (t : Ty) → Json → Option Val`,
structural on `t`, refusing at the opaque cases. Two laws, both in `Effect4.Laws`:

- `encode_of_hasTy : Val.hasTy v t → (encode t v).isSome`, so a value that inhabits a column
  always has a plain-object reading;
- `decode_encode : Val.hasTy v t → decode t (encode t v) = some v`, the round trip.

With S4b: `encode_sub : sub s t → hasTy v s → encode t v = encode s v`, so encoding at a
supertype column is the same JSON. The truth harness already renders machine values as JSON
(`harness/truth/Truth.lean:342-402`); that rendering becomes `encode` at the program's exit
type, so the harness compares under the schema rather than beside it. A day or two.

### S-4. Enforcement: the API and the printer

- `Api.schemaOf : Program → RowTable → Option Document`, defined as `typeOf` mapped through
  `EffTy.document`. It refuses exactly when `typeOf` does. Nothing new can be well-typed
  without a document; that is the enforcement, and it costs no rule.
- `printModule` emits the document as a second constant beside the program, through the
  existing `Codegen/Schema` module printer, and always emits the `Effect.Effect<A, E, R>`
  annotation. Today `printDecl` drops the annotation when the requirement row is non-empty
  (`src/Effect4/Codegen/Print.lean:457-461`); with a schema for `R` that gap closes.
- The TypeScript reflections regenerate from the same documents, so the TS side's `Ty` node
  and the schema of a `Ty` are one generated thing, not two hand copies (the DI-40 rule).

Hours for the API, a day for the printer and the regeneration.

### S-5. The gate

Two checks, both host-side, both in the truth lane:

- every corpus program's document reads back through `SchemaRepresentation.fromJson` at the
  pin, the check `harness/schema-host` already does for authored documents;
- every corpus program's recorded exit decodes under its own `Schema.Exit(…)` with
  `Schema.decodeUnknownSync`, on rc.112. This is the check that makes "the schema says what the
  program emits" a tested claim rather than a rendering.

A day.

## 4. The higher-order layer

The owner's steer is that the schema-native typings are what make `Eff` ergonomic. The
learnings since the Schema work that shape them:

- **Types are indexed by the column, not by a Lean type.** `TySchema (t : Ty)` as a
  structure carrying `encode`/`decode` at `t` with the round-trip proof, built by the
  combinators below and never by hand. This is the `Image` trait
  (`src/Effect4/Store/Image.lean`) at the boundary: a writer, a reader, and the two laws.
- **Combinators mirror rc.112's Schema module, at the `Ty` level.** `option`, `array`,
  `tuple`, `union`, `literal`, `struct` over named rows, `taggedError tag payload` for the T3
  column, `exit answer error`, `cause error`, `result`. Each is a function on `Ty` with the
  representation and the codec derived together, so a combinator can never produce a type
  and a schema that disagree.
- **Names come from the references table.** A canonical row schema is a `reference` by
  identifier, and `identifierKey` annotations (`Store/Shape.lean:409-412`) give it its name on
  the host. This is what lets the printed `Effect.Effect<…, SqlError, …>` cite a schema by
  name rather than inline the tuple.
- **The document is the unit, the CAS is the store.** A `Document` already has a `Canonical`
  instance and a content kind (`Store/Node.lean`), so a program's document is addressable
  like the program. The site's use-case node (`2026-09-10-v0-scout-cas-site.md` §3) pins
  the document beside the program bytes.
- **Nothing hand-copied.** The TS reflections, the schema modules and the row documents are
  generated from `Ty.schema` and the package tables. The fourteen hand copies of the atom
  table are the counterexample this rule exists for.

## 5. How this sits with the other eleven

- T1 (union answers): `schema (join a b)` is the union of the two schemas; S4c changes the
  join, not the schema function.
- T2 (literal widening): `lit` gets its `literal` arm; a widened `string` gets `string`.
  The printed annotation and the document agree because both come from the same `Ty`.
- T3 (tagged columns): the canonical union-of-pairs column has one document, a `union` of
  tuples with a `literal` first element. A `Data.TaggedError` class on the host projects to
  that tuple at the adapter; its schema on the host side is the adapter's, not ours, which is
  the B-row rule.
- T5 (`nat`): `number` with the integer and non-negative checks says at the boundary what the
  refusal says at admission.
- T8, T9 (defects, error image): `Defect` in the exit schema is rc.112's own; the error
  member is the closed image's schema.

## 6. Sequence and cost

S-1 and S-2 go in the same slice as S4b's `lit` arm, since `Ty.schema` wants the final
constructor list. S-3 and S-4 follow, then S-5 as a truth-lane gate. About a week in total,
none of it touching the machine, the wire, or a proof already landed. The only wire change is
none: `Document` is already a carrier.
