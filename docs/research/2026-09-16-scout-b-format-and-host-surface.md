## Part 1. `Std.Format` against the first-pass `Doc`

### 1.0 What `Format` is

Read, `~/.elan/toolchains/leanprover--lean4---v4.33.1/src/lean/Init/Data/Format/Basic.lean`.
Eight constructors (`:55`-`:107`): `nil`, `line`, `align (force)`, `text`, `nest (Int)`,
`append`, `group (behavior)`, `tag (Nat)`. It derives `Inhabited` and nothing else (`:107`): no
`DecidableEq`, no `Repr`, no `BEq`.

Four facts decide everything below. (1) **No hard-break constructor**: a hard newline is a `\n`
inside a `text`, and `be` splits at the first `\n`, emits the prefix, calls
`pushNewline i.indent.toNat` and continues (`:266`-`:281`), while `spaceUptoLine` reports it as
`foundLine` and, inside a flattened group, `foundFlattenedHardLine` (`:171`-`:174`), which stops
a group flattening around a block (`:250`). (2) **No `flatten` function and no two-sided
choice**: flattening is a `Bool` threaded through `spaceUptoLine` and read off the work group in
`be`, so the flat alternative of `group f` is always that same `f` with the flag set, and
nothing can emit a byte only in the broken layout. (3) **The tag is a `Nat`** (`:106`), not a
type parameter. (4) **`be` and `spaceUptoLine'` are `partial`** (`:252`, `:209`), so `prettyM`
(`:345`) and `pretty` (`:415`) are opaque constants, though `spaceUptoLine` (`:162`) is
structural. The `String` renderer is a `MonadPrettyFormat (StateM State)` whose
`startTag`/`endTags` do nothing (`:399`-`:405`).

### 1.1 Q1. Can the house layout be `Format`, with the same bytes?

The house renderer is `.lake/packages/typescript/TypeScript/Render.lean`. Two properties
matter: indentation is **absolute**, computed from a `depth` argument and emitted as literal
spaces (`:26`, and every `indentOf style depth` site), and inline versus multiline is
`containsNewline` over the already-rendered children (`:114`, used at `:135`, `:158`, `:186`).

**(a) Group-free `Format` reproduces the bytes at every width.** Restrict the document to
`nil`, `text` (with `\n` for hard breaks), `nest`, `append`, `tag`. Then `pushGroup` is never
reached: its only call sites are the `group` arm (`:332`) and the hard-break arm guarded by
`if g.fla == .disallow` (`:278`), and `prettyM` seeds the one work group with `fla := .disallow`
(`:346`), which nothing changes without a `pushGroup`. So `w` is never read, `currColumn` is
never read (only `align` and `pushGroup` read it), and the output is a function of the document
and the initial indent alone. The absolute indents come back as relative `nest 2`, because
`depth` rises by exactly one at each block and each multiline object arm and never otherwise
(eleven sites: `Render.lean:134`, `:151`, `:185`, `:207`, `:214`, `:245`, `:248`, `:251`,
`:255`, `:260`, `:317`). I wrote three shapes as `Format` in the scratch file (a generator body,
an inline object, an object forced multiline by a generator child) and traced `be` by hand; the
first and third give the bytes of `DocTest.withBlock` (`…/lean4-doc/DocTest/Guards.lean:33`).
Reasoning from source, not an execution.

**(b) `Format.group` cannot express the house object.** The arms are not flatten-related: inline
is `{ a: 1, b: 2 }`, multiline is `{\n  a: 1,\n  b: 2,\n}` with a **trailing comma after the last
field** (`Render.lean:144`, again at `:152`, `:167`, `:175`, `:192`).
`group (nest 2 ("{" ++ line ++ fields) ++ line ++ "}")` gives the inline bytes exactly and
`{\n  a: 1,\n  b: 2\n}` broken, one byte short, and `Format` has no primitive emitting only when
broken (1.0(2)). The comma is in five arms of `Render.expr` and in every golden. So: with
`group`, no; without `group`, yes, but the layout decision returns to the caller, the
traversal-with-state the design replaces with a fold
(`docs/research/2026-09-16-printer-reader-positions-design.md` §4).

**A third strike.** Even for flatten-related arms, `Format`'s group decision reads the width
(`:250`, `r'.space <= w-k`) and the column (`pushGroup` calls `currColumn`, `:244`), and is
**re-decided after every hard break inside a group** (`:281`), so "layout does not depend on a
viewport" is not statable about `Format`; the best available is a width so large the comparison
always passes, an assumption about the corpus. In `Doc` it is `layout_house_stream` and
`layoutAlg_house_width` (`…/lean4-doc/Doc/Laws.lean:115`, `:110`), proved. `Format.pretty` gives
the house bytes deterministically at any width only for the group-free encoding, and only as an
assumption, because the renderer is `partial` (1.3).

### 1.2 Q2. Positions from `MonadPrettyFormat`

**Yes**, and core ships one: `Lean/Widget/TaggedText.lean:84`-`:104`. `TaggedState` carries the
output, a tag stack and a column; `startTag n` pushes `(n, col, out)` and resets the accumulator
(`:94`); `endTags n` pops `n` frames and re-nests them (`:95`-`:98`); `prettyTagged` (`:103`)
returns a `TaggedText (Nat × Nat)`, a **tree**. A second instance is at
`Lean/PrettyPrinter/Formatter.lean:613`. For bytes and UTF-16 instead of a code-point column the
instance carries a `Measure`: `pushOutput s` adds `Measure.ofText s`, `pushNewline i` adds
`Measure.newline i` (`Doc/Measure.lean:59`, `:67`), `startTag` records the running measure,
`endTags n` closes `n` frames. Nothing in the class blocks it. One constraint:
`currColumn : m Nat` (`Basic.lean:232`) feeds `align` and the flatten test, so it must return the
display column, which with a product measure is the `columns` projection.

**Is the tag stream well-bracketed by construction? No.** It is well-bracketed in practice, by a
discipline inside `be` that no type records: `append` gives the **left** operand
`activeTags := 0` and lets the **right** inherit the count (`:264`), so a tag closes at the
rightmost leaf of its subtree; every leaf arm calls `endTags i.activeTags` (`:258`, `:269`,
`:288`/`:292`/`:297`/`:306`, `:315`/`:321`/`:324`); and `endTags` takes a **count**, not a tag,
so the instance keeps its own stack and trusts the count. Three ways that breaks: an instance
that short-circuits leaves tags open (the `OneLine` instance throws out of `pushOutput` and
`pushNewline`, `Formatter.lean:619`-`:637`, and patches the unclosed tags afterwards from
`s.tags`); the `TaggedText` invariants that make the tree well-formed are stated in a
**docstring** (`TaggedText.lean:24`-`:27`) and enforced nowhere; and `be` is `partial`, so there
is no induction principle to prove the discipline with.

Compare: `Doc.Bracketed` is an inductive predicate (`Doc/Layout.lean:154`) and
`Doc.layout_bracketed` is **proved** for every policy, width, indent and column
(`Doc/Laws.lean:87`, nineteen lines). That theorem is what makes `locate`
(`Doc/Layout.lean:150`) a descent rather than a search that happens to work.

### 1.3 Q3. What is lost, and what matters downstream

| law (design §9) | in `Doc` | in `Format` |
| --- | --- | --- |
| 1. monoid under `cat` | proved at the layout: `Doc/Laws.lean:43`, `:47`, `:51` | unprovable: the statement is about `pretty`, which is `partial` |
| 2. `nest` homomorphism | proved: `Doc/Laws.lean:57`, `:61` | unprovable, same reason |
| 3. flatten laws | proved by `rfl`, eight (`Doc/Core.lean:143`-`:150`) | **not statable**: there is no `flatten : Format → Format` |
| 4. measure is a monoid homomorphism | proved: `Doc/Laws.lean:66`, with `Doc/Measure.lean:41`, `:48`, `:51` | no measure exists; `SpaceResult`/`merge` (`Basic.lean:149`, `:155`) short-circuits at the first line and threads a width, so it is not a monoid |
| 5. stream well-bracketed, spans a tree | proved: `Doc/Laws.lean:87` | a discipline of a `partial` function (1.2) |
| 6. house policy ignores its state | proved: `Doc/Laws.lean:110`, `:115`, `:137` | false as stated for `group`; true but unprovable group-free |

**4 and 5 matter most.** 5 is the correctness statement of the position table, and S3 ("blame to
code by span containment") is meaningless without it: unbracketed, `spans` could overlap and
`locate`'s `find?` picks whichever comes first. 4 is what makes §8's incremental re-render cost
the depth rather than the size, and what lets `text ∘ render_house = Render.expr` (§9 item 13)
be proved by fusion (`Doc.cata_fusion`, `Doc/Core.lean:120`) instead of a brute mutual induction
over `Render.expr`'s seventeen arms. **6 is the byte-determinism claim**: the goldens check it by
example on 408 programs, the lemma covers every program a future generator emits, twenty-one
lines. **1, 2 and 3 are hygiene for the author of a render algebra**: nothing downstream breaks
without them, but they let you refactor a `nest` or re-associate a concatenation without
re-running the goldens, and 2 and 3 are exactly the laws
`docs/ALGEBRAIC-LAYOUT-ENGINES.md:109`-`:117` demands of the one-dimensional core. **Executed
anyway**, whichever carrier wins: the goldens' byte identity, the span agreement against `tsgo`,
the diagnostics lane.

**A fourth loss: `#guard` versus `decide`.** `#guard` evaluates with `unsafe evalExpr`
(`Lean/Elab/Tactic/Guard.lean:166`), the compiler, so `#guard Format.pretty f 120 = "…"` works.
But `rfl`, `simp`, `decide` and `decide +kernel` cannot see through a `partial def`, and
`native_decide` adds `Lean.ofReduceBool`, outside the `[propext, Quot.sound]` ceiling
(design §9). Since the same design wants kernel `decide` for the template table's disjointness
(§9 item 9) and the syntax table's shape (item 7), a carrier opaque to the kernel is one the
proof graph cannot reach. Separately `Format` has no `DecidableEq` (`Basic.lean:107`), so a
`#guard` comparing two documents is not even well-formed.

**`Doc` as the proved reference with `Format` as the runtime?** Buildable, and it should be
refused. The design's first paragraph names the current situation as the problem: hand-written
recursions "that agree by testing" (design §1). Two renderers with an executed agreement is that
situation again with more surface, and the trade has no upside: `Format` cannot express the
house choice (1.1b), its annotation is a `Nat` needing a side table (1.0(3)), its renderer is
opaque (1.3). `Doc` is 694 lines including laws and guards (tested), smaller than either renderer
it replaces. The one honest, non-duplicating use is a one-way `Doc A → Format` export so a
program, a refusal or a containment tree can be shown inside Lean's own message infrastructure
(`ToFormat`, `MessageData`, `#eval`): no law attached, about fifteen lines.

### 1.4 Q4. The two-dimensional engine

The one-dimensional core the specification needs is exactly `Doc`.
`docs/ALGEBRAIC-LAYOUT-ENGINES.md:109`-`:117` lists four laws (monoid of concatenation,
indentation homomorphism, horizontal distributivity, `group(D) = flat(D) ⊓ D`). `Doc` has all
four (`Doc/Laws.lean:43`/`:47`/`:51`, `:57`, `:61`, and `Doc.group` at `Doc/Core.lean:141` is
literally `choice (flatten d) d`). `Format` gives the first two only as unprovable statements
about `pretty`, and the fourth with `flat` not a function.

The elastic policy needs more than `Format` offers.
`docs/ALGEBRAIC-LAYOUT-SPECIFICATION.md:37` cites Bernardy's **Pareto frontier of measures**,
which requires the measure to be a value you can compare and prune on; `Format` computes a
`SpaceResult` (`Basic.lean:149`) with one `space` field and two booleans, discards it, and
offers no hook. `Doc.Policy` (`Doc/Layout.lean:37`) takes the `Info` of both alternatives and
`Doc.elastic` (`:99`) is the greedy resolution, so a Pareto policy is a different `Policy` over
a richer carrier: a change of one field. The badness cubic and `badnessThreshold`
(`SPECIFICATION.md:74`, `:218`) need a numeric measure at the choice point, same argument.
`Glue`, `Envelope`, `Tile`, `FiberSpan` and the tropical path are two-dimensional and share only
the widths; that layering is right and unaffected. So `Format` does **not** suffice for the
one-dimensional core and the custom `Doc` does, and the containment tree
(`SPECIFICATION.md:242`) is one more `Doc`-valued fold with the same path annotations, the
unification the design claims in §7, which `Format`'s `Nat` tag would make indirect.

The four defects design §7 names are still in the specification and none is about `Doc`:
`Glue.resolve` cancels its own stretch (`SPECIFICATION.md:325`-`:334`), `allocateLanes` is
`mapIdx (fun idx s => (s.fiberId, idx))`, the staircase it exists to prevent (`:520`-`:526`),
`terminalAspectScale : Float` has no decidable equality (`:226`), `Envelope.empty` uses a large
negative sentinel.

### 1.5 Q5. Recommendation

**Take the custom `Doc` as the runtime carrier. Do not use `Std.Format` for the printer, the
positions or the layout engine. Keep one thin `Doc → Format` export for Lean-side display.**

The reason in one line: the house layout needs a choice between two *different* documents (the
trailing comma) and `Format.group` offers only a document against its own flattening, and the
six laws the proof graph rests on are statements about a renderer that in `Format` is `partial`
and invisible to the kernel. The cost, stated fairly: `Format` would buy the `ToFormat`
ecosystem and about 470 lines of a tuned Wadler engine with `fill` behaviour, and would cost the
whole §9 P5 block plus the fusion lemma that makes item 13 cheap. Not a close call.

Two amendments to the first-pass package, from reading it against `Render.expr`.
(1) `Doc.infoAlg.text` measures `s.length` (`Doc/Core.lean:165`), code points, while
`Measure.ofText` carries bytes, UTF-16 and columns separately (`Doc/Measure.lean:59`). Code
points is right for the elastic comparison, but the two widths should be named apart or a reader
takes `flatWidth` for a byte count; the `#guard` at `DocTest/Guards.lean:51` compares
`measure.utf16` with `String.length`, which coincide only on the basic plane, and on ASCII, which
the corpus is, all three coincide. (2) `Doc.Item` (`Doc/Layout.lean:26`) has no hard-break item:
both `line` and `hardline` lay out as `.newline i` (`:47`, `:48`). That is right for the stream
and means `Bracketed` and `spans` need not know the difference, but it deserves a sentence,
because `hasHardline` (`Doc/Core.lean:179`) suggests otherwise.

## Part 2. The generated host surface

### 2.1 The CLI shapes a generator must target

Read, `vendor/effect-4.0.0-rc.112/src/unstable/cli`.

`Command<Name, Input, ContextInput, E, R>` (`Command.ts:120`) is itself an
`Effect.Effect<ContextInput, never, CommandContext<Name>>` carrying `name`, `description`,
`shortDescription`, `alias`, `examples`, `subcommands`, `annotations : Context.Context<never>`,
`unlisted`. `Command.make` has four overloads (`:713`, `:807`, `:901`, `:1088`): bare name; name
plus `Config`; name, `Config` and effectful handler; handler-first for piping. `Command.Config`
(`:197`) is a record whose values are `Param.Param`, arrays of those, or nested `Config`s, and
`Config.Infer` (`:213`) is the parsed record type, so a generator emits an object literal and
nesting is free. `Command.withSubcommands` (`:1218`) takes subcommands with an optional group
name; `Command.run` (`:2767`) and `Command.runWith` (`:2981`) take `{ version, renderErrors? }`
and an argv array, and require `Environment` (`:2989`: FileSystem, Path, Stdio, Terminal,
ChildProcessSpawner).

`Flag` (`Flag.ts:35`) and `Argument` (`Argument.ts:41`) are `Param` at a fixed kind
(`Param.ts:54`, `"argument" | "flag"`), with sixteen primitive constructors (`string`, `boolean`,
`integer`, `float`, `date`, `choice`, `choiceWithValue`, `path`, `file`, `directory`, `redacted`,
`fileText`, `fileParse`, `fileSchema`, `keyValuePair`, `none`; `Flag.ts:57`-`:442`,
`Argument.ts:62`-`:297`) and the usual combinators (`withDescription`, `withAlias`,
`withMetavar`, `withDefault`, `optional`, `variadic`, `between`/`atLeast`/`atMost`, `filter`,
`map`, `mapEffect`, `orElse`, `withFallbackConfig`, `withFallbackPrompt`).

**How a `Schema` types an argument: two ways, and they differ.**
`Param.withSchema(self, schema)` (`Param.ts:2617`) takes a
`Schema.ConstraintCodec<B, A, Environment, unknown>` and refines `Param<Kind, A>` into
`Param<Kind, B>`, turning a decode failure into `CliError.InvalidValue` with the option name and
the expected text. `Param.fileSchema(kind, name, schema, options)` (`Param.ts:832`) builds the
parameter *from* a schema by reading a file and decoding it. The first is for scalars, the
second for a JSON manifest argument. So a generator needs, per tool: a name, a description, a
list of `(field, kind, primitive, schema?, description, default?, optional/variadic)`, and a
handler body. That is a table.

### 2.2 The MCP shapes

Read, `vendor/effect-4.0.0-rc.112/src/unstable/ai`.

`Tool.make(name, options)` (`Tool.ts:1204`) with
`{ description?, parameters?, success?, failure?, failureMode?, dependencies?, needsApproval? }`,
the schema slots being `Schema.Constraint` defaulting to `EmptyParams`, `Schema.Void`,
`Schema.Never`. The `Tool` (`Tool.ts:197`) carries `id`, `name`, `description?`, `failureMode`,
`parametersSchema`, `successSchema`, `failureSchema`, `annotations`. `Toolkit.make(...tools)`
(`Toolkit.ts:496`) collects them by name into `Toolkit<Tools>` (`:65`), and
`McpServer.toolkit(toolkit)` (`McpServer.ts:1609`) is `registerToolkit` (`:1515`) over
`McpServer.layer`.

`registerToolkit` is where the schemas become the wire contract (`:1533`-`:1545`):
`Tool.getJsonSchema(tool)` gives `inputSchema`, and
`Tool.getJsonSchemaFromSchema(tool.successSchema)` gives `outputSchema` **only when that JSON
Schema has `type: "object"`** (`:1535`-`:1538`). A hard constraint on the generator: a tool whose
success is a bare string publishes no output schema, so a text projection must be wrapped in an
object if the agent is to see its shape. The MCP annotations come from the Effect context,
`Tool.Title`, `Tool.Readonly`, `Tool.Destructive`, `Tool.Idempotent`, `Tool.OpenWorld`
(`:1550`-`:1558`), all table columns.

Transports: `McpServer.layer` (`:1157`) over an `RpcServer.Protocol`; `layerStdio` (`:1207`)
wrapping it in `RpcServer.layerProtocolStdio` with JSON-RPC over NDJSON; `layerHttp` (`:1317`);
all three taking `{ name, version, description?, websiteUrl?, icons?, protocols, extensions? }`.
Beyond tools: `registerResource`/`resource` (`:1673`, `:1882`), `registerPrompt`/`prompt`
(`:1981`, `:2106`), `elicit` (`:2144`). `resource` is the right home for the corpus, the census
and the agreement tables; `prompt` for a worked authoring example.

### 2.3 Schema AST compilers as the consumption idiom

`SchemaAST.AST` is a 22-way union (`SchemaAST.ts:53`-`:74`): `Declaration`, the ten keywords
(`Null`, `Undefined`, `Void`, `Never`, `Unknown`, `Any`, `String`, `Number`, `Boolean`,
`BigInt`), `Symbol`, `Literal`, `UniqueSymbol`, `ObjectKeyword`, `Enum`, `TemplateLiteral`,
`Arrays`, `Objects`, `Union`, `Suspend`. Every node extends `Base` (`:636`) carrying
`annotations`, `checks`, `encoding`, `context`, and `Schema.Annotations.Annotations` is an open
record `readonly [x: string]: unknown` (`Schema.ts:17004`) extended by module augmentation
(worked example at `:16979`): the host-side extension point for the design's grammar annotation.

`Arbitrary` is `internal/schema/toArbitrary.ts`: `memoized` (`:471`) over `recur`, a `switch` on
`ast._tag` with one arm per kind (`:505`-`:808`), a plain fold with memoization for `Suspend`.
That is the idiom to copy. `JsonSchema.ts` is the other half: the interface (`:30`), dialects
(`:55`), `Document`/`MultiDocument` (`:129`, `:153`), dialect rewrites (`:282`-`:598`),
`rewriteRefs` (`:739`). `SchemaRepresentation.ts` is the persisted form: `Representation`
(`:406`), `Document` (`:480`), `MultiDocument` (`:491`), revivers (`:502`-`:566`), and it is the
exact upstream that `src/Effect4/Schema/Representation.lean` and `Document.lean` pin, which is
why the schema printer can be a second template table over the same `Tree`. There is no `Pretty`
module in rc.112 (tested: no `Pretty.ts` under `src/`); the analogue is `Formatter.ts:41`,
`Formatter<Value, Format>`, which is issue-shaped rather than value-shaped.

### 2.5 Two of them as a generated CLI

`corpus` and `tsdiag` cover both argument shapes: positional plus scalars, and a promote switch
that rewrites a committed file.

```ts
const corpus = Command.make("corpus", {
  dir:     Argument.directory("dir", { mustExist: false })
             .pipe(Argument.withDescription("where the printed corpus is written")),
  count:   Flag.integer("count").pipe(Flag.withDefault(400)),
  depth:   Flag.integer("depth").pipe(Flag.withDefault(4)),
  styles:  Flag.boolean("styles").pipe(Flag.withDefault(false)),
  foreign: Flag.boolean("foreign").pipe(Flag.withDefault(false))
}, (c) => runDriver("tools/Tools/Corpus.lean", argvOf(c)))

const tsdiag = Command.make("tsdiag", {
  corpusDir: Argument.directory("corpus-dir"),
  workDir:   Argument.directory("work-dir", { mustExist: false }),
  promote:   Flag.boolean("promote").pipe(
               Flag.withDescription("rewrite generated/tsdiag-agreement.tsv"),
               Flag.withDefault(false))
}, (c) => runTsdiag(c))

export const run = Command.runWith(
  Command.make("effect4").pipe(Command.withSubcommands([corpus, tsdiag])),
  { version: "0.1.0" })
```

`--promote` is the only place in the inventory where a driver rewrites a committed file on
purpose, so the table needs a `destructive : Bool` column, and it is the column MCP's
`Tool.Destructive` reads (`McpServer.ts:1553`). The `corpus` handler's output is a directory
plus an index, a `Resource` in MCP terms and a path in CLI terms: one column, two projections.

### 2.8 The host reader from an exported table over `tsgo`'s AST

**The table.** Tested, with a script over
`/opt/homebrew/lib/node_modules/@typescript/native-preview/dist/ast/ast.generated.d.ts`: 220
exported interfaces, 192 with a concrete `kind: SyntaxKind.X`, 28 base interfaces with no kind.
Flattening `extends` and dropping brand and flag fields (`_*Brand`, `flags`, `modifierFlags`,
`tokenFlags`, `fullSignature`) gives **482 field slots across 192 kinds, 202 optional, 132
`NodeArray`, over 112 distinct field names**, and no kind with zero fields. `SourceFile` is
declared in `ast.d.ts:47`, not the generated file, so it is a 193rd kind to add.

**The first trap.** A naive import reading only each interface's own body gets 301 slots and is
wrong: `PropertyAssignment` (`ast.generated.d.ts:555`) has no `name` of its own (it comes from
`NamedMemberBase`), `WhileStatement` has no `statement`, `FunctionExpression` has neither
`parameters` nor `typeParameters`. Twenty-eight base interfaces must be flattened; tested both
ways, 301 versus 482.

**What a generic matcher needs, per kind.** (1) the kind name and its `SyntaxKind` number, which
`formatSyntaxKind` (`utils.d.ts:3`) lets you dump rather than transcribe; (2) the ordered field
list with `optional` and `multiple`; (3) the union of kinds admissible in each field, so a match
fails early; (4) which fields are punctuation tokens (`questionDotToken`, `asteriskToken`,
`equalsGreaterThanToken`, `colonToken`), because `forEachChild` flattens them into the child
stream; (5) the layout discriminants `ObjectLiteralExpression.multiLine : boolean` (`:546`),
`Block.multiLine` (`:237`-`:240`) and `NodeArray.hasTrailingComma?` (`ast.d.ts:25`).

Point 5 is a real discovery: TypeScript's own tree records **both** layout facts the house
printer decides, whether an object literal is multiline and whether its element list carries a
trailing comma. So the house layout is expressible as data on the imported tree, not only as a
`Doc` choice; S2's span check can compare those two booleans instead of rendered bytes; and a
`Tree` built from the table carries the house's decision losslessly, which answers the objection
that the printed image's layout lives outside the syntax.

**One normalisation per engine.** `tsgo`: offsets are UTF-16 code units into `sourceFile.text`,
and a node's start is `getStart()`, which skips leading trivia, while `pos`/`getFullStart()`
includes it (`ast.d.ts:35`-`:37`). Normalise by taking `getStart()`/`getEnd()` and never `pos`,
building paths by **named field and index within that field** and never by `forEachChild`
ordinal, and comparing modulo `skipOuterExpressions`, since our image emits no parentheses.
Containment lookup is free: `getTokenAtPosition`, `getTouchingToken`, `findPrecedingToken`
(`astnav.d.ts:2`-`:4`). `oxc`: offsets are UTF-8 bytes and the ESTree names differ
(`MemberExpression`, `Property`, a different type-arguments key), so the normalisation is a
byte-to-UTF-16 remap plus a kind and field renaming table, both documents; read only, from the
precedents note §5b(4), I did not run oxc. Since all 408 printed corpus programs are ASCII (that
note's §5b(4), not re-run here), the units coincide on our own image and the normalisation earns
its keep only for foreign code.

### 2.9 Risks, and a staged order

1. **The syntax table drifts with the compiler.** It is a generated file under `make check-gen`,
   its producer names the compiler version, and `HostConfig.version` (`Diagnostics.lean:37`) is
   already checked before every tsdiag run (`run-tsdiag.mjs:43`).
2. **The base flattening is silently wrong** (28 bases, 181 inherited slots). Mitigation: a
   `#guard` counting kinds, slots, optional and multiple, 2.8's four numbers.
3. **The `ToolSpec` table and the drivers drift apart.** Mitigation: generate each driver's
   `parseArgs` *from* the table, as `NodeLenses.lean` is generated from `binders.json`
   (`src/Effect4/Program/NodeLenses.lean:1`-`:4`, stamped).
4. **The MCP output-schema rule** (`McpServer.ts:1536`): guard that every success row is a
   struct.
5. **`Environment` for the CLI is heavy** (`Command.ts:2989`): a generated CLI that only shells
   out still pays for it. Not a blocker, but it is why the CLI comes after the toolkit.
6. **The drivers are Lean processes.** Every run is a `lake env lean --run`, seconds not
   milliseconds, and the estate's rule is one Lean compiler at a time; a server fronting them
   must serialise them and say so in its tool descriptions.

Order, respecting "everything generated, nothing hand-written that could be data": **H1** the
`ToolSpec` document, one Lean record per driver with 2.4's columns under `src/Effect4/Tooling/`,
with a `#guard` that every path it names exists, and no emitter yet; **H2** generate each
driver's `parseArgs` and usage string from its `ToolSpec`, so the table is load-bearing and
cannot rot (`tools/Effect4Gen/Driver.lean:150` is the model); **H3** the refusal and authoring
schemas into `ts/eff/` (`TypeReason`, `TypeRefusal`, `AuthorRefusal`, `Authoring.Src`, `Span`,
`Role`), a one-line addition to `TsGen`'s family list plus regeneration; **H4** the MCP toolkit
from H1 and H3, stdio, five tools, the agent unlock, before the CLI because it needs less of
`Environment`; **H5** the imported syntax table with risk 2's guard and the generic matcher over
it, design S2 and S6; **H6** the generated CLI from the same table; **H7** `ToolOp` rows answered
by the tape (design §5, a direction not a stage), since once H1 exists a driver run is a row with
a request and an answer, which `NativeOp.external` and `RowTable` already replay.

## Part 3. The three additions

### 3.1 Coloring as a second annotation on the stream

The design system fixes **four hues and no fifth**
(`docs/UNIFIED-DESIGN-SYSTEM-SPEC.md:83`-`:93`): `--ink-machine` for the machine, pure values,
AST and syntax; `--host-amber` for the host's hand, the decision tape, bar lines and external
inputs; `--failure-madder` for causes, typed failures and unhandled exits;
`--resource-verdigris` for scopes, finalizers, leased handles and lifetime brackets. Double
encoding is a contract (`:158`-`:165`): glyph plus hue, never hue alone, with the glyph lexicon
(`:109`-`:126`) binding each glyph to a named Lean constructor.

**The role fold.** `Effect4.Program.foldMapAt_eff` (`src/Effect4/Program/Fold.lean:1654`)
already visits every node of the mutual family with its path, threading `p ++ [i]` at each
child, with one callback per sort. A role fold is that fold at `M = List (List Nat × Role)`,
`unit = []`, `op = (++)`, over a per-constructor `Role` table: `fail`, `failCause`,
`yieldError`, `catchCause`, `matchCause`, `catchIf` are failure; `scoped`, `acquireRelease`,
`onExit`, `provideLayer`, `provideService`, `closeScope`, `forkScoped` are resource; `perform`,
`callback`, `sleep`, `clockNow`, `external` are host; everything else is machine. One generated
row per `Eff`, `Stmt`, `ActionTerm` and `LayerTerm` constructor, from the generator that already
emits `NodeLenses` and `binders`.

**Attaching it.** Make the annotation a **pair**, `Doc (Path × Role)`. `Doc A` is polymorphic in
`A` (`Doc/Core.lean:25`), so this costs nothing: `spans` returns `Span (Path × Role)`
(`Doc/Layout.lean:132`), `locate` returns `Option (Path × Role)` (`:150`), ANSI reads both, HTML
emits a class from the role and a `data-path` from the path, plain text ignores both. Double
encoding then has a mechanical form: **the text projection must be recoverable from the stream
without reading any role**, true by construction because `Doc.string` (`Doc/Layout.lean:126`)
maps `push`/`pop` to `""`. That is the strongest version of "an agent never receives a picture
it cannot read". The alternative, `Doc Path` plus a side map `Path → Role`, is equivalent but
puts the two facts in two places and needs a lemma that the key sets agree.

**Can `Format`'s `tag : Nat` carry both?** Only through an index into a side array, which is what
core does (`TaggedText.lean:103` returns `TaggedText (Nat × Nat)`, the tag meaning "look me up").
The cost is not the indirection but that the document stops being self-describing: you cannot
compare two documents, you cannot `#guard` one without also comparing the side array, and an
incremental re-render must keep the indices stable. With 1.1(b), a second independent reason to
keep the custom `Doc`.

One caution: `foldMapAt_eff` visits **node** children only. Terms are not nodes
(`src/Effect4/Program/Node.lean:16`-`:26`, and `NodeLenses.lean:16`), so a role fold gives a role
for `Effect.fail(e)` but not for the `e` inside it. See 3.2.

### 3.2 One coordinate system

**The coordinate exists and it is `List Nat`**: `Node.child`'s index path
(`src/Effect4/Program/NodeLenses.lean:19`, generated), addressed by `Node.at_`
(`src/Effect4/Program/Refs.lean:44`), ordered by `Path.lt` and `Path.properPrefix` (`:73`,
`:80`), used by `Eff.refSites` and `Eff.layerPaths` (`:110`, `:164`), threaded by
`foldMapAt_eff` (`Fold.lean:1654`), reported by `Api.blame` (`Api.lean:120`) and
`TypeRefusal.path` (`Typing/Blame.lean:94`), recorded per corpus program in
`generated/corpus-index.tsv` and `generated/tsdiag-agreement.tsv` (stamped; the `path` column,
for example `g10 false term 0.0`), and carried as a layer's identity (`Node.lean:22`: "its path
is its identity"). Scope depth indexes off the same path via `Node.binders`
(`src/Effect4/Program/Binders.lean:18`).

**What the MCP schemas must carry.** `path : Schema.Array(Schema.Number)` on every node-shaped
input and output, never a line and column, never an offset alone.
`span : { startByte, endByte, startUtf16, endUtf16 }` on any output naming printed text, because
the host counts UTF-16 (`ast.d.ts` offsets) and Lean counts bytes (`String.Pos`) while
`Doc.Measure` carries both (`Doc/Measure.lean:16`): give both and no client has to know which
engine produced it. `reason : TypeReason` as a tagged union plus `head : String`
(`Typing/Blame.lean:28`, `:67`) and `codes : Array<number>` from `codesOf`
(`Diagnostics.lean:87`), so a refusal is legible both as this machine's reason and as the host
compiler's diagnostic. `text` plus `lines : Array({ path, depth, role })` on every visual
projection, which is 3.1's contract in schema form. And the profile stamp from
`ts/eff/profile.gen.ts` on the initialize response, so a client can refuse a mismatched grammar.

**What makes the coherence executable.** **Check A, one path set**: for every corpus program,
let `P` be the paths `foldMapAt_eff` yields; then the printed document's `spans` project onto
exactly `P`, the containment tree's lines project onto exactly `P`, `Api.blame` when it answers
is in `P`, every diagram mark's path is in `P`, and `Node.at_` succeeds on exactly `P`. Five
decidable finite-set equalities per program over the 408 of `.lake/corpus`; that is what turns
"one coordinate system" from an intention into a lane. **Check B, commuting with `Node.child`**:
for every projection `π`, path `p` and index `i` with `Node.child (at_ n p) i = some c`, the
mark `π` gives `p ++ [i]` is contained in the mark it gives `p`. For the `Doc` that is
`layout_bracketed` (`Doc/Laws.lean:87`) plus the render algebra's annotation discipline, so
provable; for the diagram it stays executed.

**The one gap, and it needs a ruling.** Terms are not nodes, so `List Nat` does not name a term
subexpression, yet the printed text has spans for them (the `3` of `Effect.succeed(3)`) and
`TypeReason.term` blames a whole node for a term's failure (`Typing/Blame.lean:31`, `:101`).
(a) Annotate with `Option Path`: term text sits inside the enclosing node's span and carries none
of its own, the coherence checks hold unchanged, the agent gets node granularity. (b) Extend the
coordinate to `List Nat × Option TermPath`, a second child lens over `Term`: the honest one.
(c) Promote `Term` to a `Node` sort, which changes `Node`, `NodeLenses`, `binders`, `foldMapAt`
and every path in every committed table; I would not.
**Recommendation: (a) now, (b) when `explain`'s `term` refusals must point inside a term.**

The OCaml face is not a spike: `ocaml/README.md:1`-`:17` says OCaml is the primary host of the

**The structural fact: the OCaml and TypeScript emitters already read the same closed world.**

In order of how nearly free it is. **The syntax table** (2.8) is pure data: an OCaml variant plus
accessors, the shape `eff_types.ml` already has. **The code table** (`codesOf`,

`eff_native.ml` already emits as data, and that is what lets an OCaml-side checker report the

turns the OCaml face from a wire codec into a full printer and reader. **The `ToolSpec` table**
would give an OCaml CLI over `cmdliner`, lower value because the drivers are Lean processes
either way. **Not the MCP toolkit**: rc.112's `McpServer`, `Tool` and `Toolkit` are TypeScript

implementation sharing only the JSON. The right OCaml face of the agent surface is to answer the

`protocol.gen.ts` and `tape.schema.json`: one protocol document, two servers, one generated
TypeScript.

**Tree-sitter's OCaml binding.** The owner's binding is `/Users/pooks/Dev/lean4-tree-sitter`

## The recommendation

**Part 1.** Use the custom `Doc` as both the runtime carrier and the proved reference. Do not
adopt `Std.Format`, and do not run the two side by side. Four independent reasons: the house
layout needs a choice between two *different* documents (the trailing comma, `Render.lean:144`
and four more) and `Format.group` offers only a document against its own flattening;
`Format`'s group decision reads the width and the column and is re-decided after every hard
break (`Basic.lean:250`, `:281`), so width-independence is not statable; `Format.tag` is a `Nat`,
so a `(path, role)` annotation needs a side table and the document stops being comparable; and
`be` is `partial` (`:252`), so none of the six P5 laws can be proved and neither `decide` nor
`decide +kernel` sees through the renderer. `Doc` proves all six in 694 lines. Keep one thin
`Doc → Format` export for Lean-side display, with no law attached, plus the two amendments of
1.5.

**Part 2.** The host surface is a table plus emitters, and most pieces exist: Effect Schemas for
all 28 families of the program IR, the image profile with a content stamp, the session protocol
as data, a schema printer for `Document`. Missing: one `ToolSpec` per driver, the refusal and
authoring schemas, one emitter. Build H1 to H7 of 2.9, the table first so the drivers' own
argument parsing is generated from it and cannot rot. Two hard facts a builder must not miss: a
tool's success must be an object schema or MCP publishes no output schema
(`McpServer.ts:1536`), and the imported syntax table is 192 kinds and 482 field slots only after
flattening 28 base interfaces, a naive import being short by 181 (tested).

**Part 3.** Make the annotation `Path × Role`, generate the role table from the constructor list
as `NodeLenses` is generated, and leave the text projection a function that ignores the role,
which makes double encoding true by construction rather than by review. Make `List Nat` the
single coordinate in every MCP schema, beside a span carrying bytes and UTF-16 together, and
make the coherence executable with Check A of 3.2. One real gap: terms are not nodes, so no path
names a term subexpression; annotate with `Option Path` now and rule later. For OCaml, the
syntax table, the code table, `HostConfig` and the template table are generatable from the
documents that already feed `TsGen` and `EffGen`; the template table is the one worth doing,
because it turns the OCaml face from a wire codec into a printer and reader. Do not generate an
MCP server to OCaml; serve the same host-session protocol document. Tree-sitter's OCaml grammar
is not pinned and should be added only when foreign OCaml must be read.
