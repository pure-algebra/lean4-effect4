# STM and transactions: rc.112's rules, and a smaller design for this machine (2026-09-19)

The owner asked for rc.112's transactions to be mapped exactly, and whether this machine, whose
programs are first-order data, can give the same observable behaviour with less machinery than
rc.112's journal. This is a read-only scout. It changes no code and runs nothing. The source was
read at `72698899`, whose source files are those of `23e668b0` (the last commit adds notes
only). Every proposal here comes after the typed-state milestone and touches none of its files.

Evidence words. **Read**: I read the cited lines. **Inferred**: I derived it from lines I read;
it has not been run or proved. Nothing below is **reproduced** (no rc.112 program was run) or
**proved** (no Lean was written or built). Host citations are paths under the vendored source;
tree citations are paths under the repository root.

## 0. The answer

rc.112's STM is a short section of `vendor/effect-4.0.0-rc.112/src/Effect.ts` (`:24177-24403`)
plus one cell type, `TxRef`. There are eleven `Tx*` modules; `TxRef` is one of them, and the
other ten are library code over it with `Effect.tx` and `Effect.txRetry`. None of the ten holds
state beyond `TxRef` cells and a few constants. The journal and the
version counters exist for one reason: rc.112's run loop can let another fiber commit while a
transaction's body is still running. That happens at a yield the op budget or a custom scheduler
injects, at a park inside the body, or when the body completes a `Deferred` whose waiter then
runs inside the completing call.

This machine can close that window with two things. The first it already has: rc.112's
`PreventSchedulerYield` reference, which the machine honours and whose effect is proved
(`injectYield_prevented`, `src/Effect4/Laws/Machine/Clauses.lean:111-115`). The second is a
fold over the transaction body that admits only
bodies that cannot park, fork or resume another fiber. Under both, no other fiber runs between
a transaction's first access and its commit (inferred). Every version check would then pass,
so versions carry no information and can go. The journal shrinks to a write buffer and a list
of accessed cells, which exist only while one transaction runs, and at most one runs at a time.
What is left to add is the kind of thing Queue or Semaphore needs: one store family on the
existing wake protocol (a value and a waiter list per cell), its rows, and one short-lived
record for the open transaction. The retry wait and its wake can follow rc.112 exactly.

This design is exactly rc.112 running each transaction under `PreventSchedulerYield`. It loses
only the behaviours that need a transaction body interleaved with another fiber: a body run
again because its reads went stale, a stale state read by an attempt that will be thrown away,
and a lost wakeup in rc.112's retry (inferred, not reproduced). For bodies whose only effects
are `TxRef` operations and pure computation, only the lost wakeup is visible in the observation
the theorems compare.

The map note's §8 says STM "would add a new kind of state"
(`docs/research/2026-09-19-stores-and-event-log-map.md:405-407`). That holds only if the
machine must copy rc.112's preemptible transactions step for step. Even then the journal is
first-order data, a map from cell to version and value. What is really new about STM is
control, not state: a body that runs again with its transactional writes thrown away.

## 1. rc.112's transactions, as rules

### 1.1 The surface

| export | where | what it is |
| --- | --- | --- |
| `Effect.Transaction` | `vendor/effect-4.0.0-rc.112/src/Effect.ts:24211-24223` | a `Context.Service` whose value is `{ retry: boolean, journal: Map<TxRef, { version, value }> }` |
| `Effect.tx` | `vendor/effect-4.0.0-rc.112/src/Effect.ts:24271-24311` | the transaction boundary |
| `Effect.txRetry` | `vendor/effect-4.0.0-rc.112/src/Effect.ts:24397-24403` | give up this attempt and wait |
| `TxRef.make`, `makeUnsafe` | `vendor/effect-4.0.0-rc.112/src/TxRef.ts:101`, `:128-136` | a new cell |
| `TxRef.modify`, `update`, `get`, `set` | `vendor/effect-4.0.0-rc.112/src/TxRef.ts:225-242`, `:334-337`, `:368`, `:460-463` | access, all through `modify` |

There is no `orElse`, no `check` and no transaction-level `catch`: neither the transaction
section nor any `Tx*` module defines one. Outside `Effect.ts` and the `Tx*` modules, nothing
uses `Effect.Transaction`, `Effect.tx` or `Effect.txRetry` (read, by search). The earlier ruling
that called `TxRef` "a separate subcalculus with read/write/retry/orElse/commit" came from
another calculus (`docs/research/2026-09-07-lit-siblings.md:166`, `:172`). The subcalculus
rc.112 actually has is smaller.

### 1.2 State

- **The cell.** `TxRef<A>` is `{ version: number, pending: Map<unknown, () => void>, value: A }`.
  `version` starts at 0, and `pending` holds one wake callback per waiting transaction
  (`vendor/effect-4.0.0-rc.112/src/TxRef.ts:61-67`, `:128-136`). It is a JavaScript `Map`, which
  iterates in insertion order, so the waiters of a cell are woken in registration order.
- **The transaction record.** The value of the `Transaction` service: a retry flag and a
  journal holding one entry per *accessed* cell, `{ version, value }`, in first-access order
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24211-24223`). There is no separate read set and
  write set: a read makes the same entry a write does.

### 1.3 Rules

**T1. Allocation.** `TxRef.make(a)` is `Effect.sync(makeUnsafe(a))`. It is not journaled and
never undone. A body that runs again allocates again
(`vendor/effect-4.0.0-rc.112/src/TxRef.ts:101`, `:128-136`).

**T2. Access.** `TxRef.modify(r, f)` does the following in one synchronous step. If `r` has no
journal entry, it adds `{ version: r.version, value: r.value }`. It applies `f` to the entry's
value, stores the new value in the entry, and answers `f`'s result. `get` is `modify` with
`[current, current]`, so a read writes back the value it read; `update` and `set` are `modify`
too. So a transaction reads its own writes, a cell's first access records the committed value
and version at that moment, and nothing checks that the values read belong to one consistent
state. Outside a transaction, `modify` is wrapped in `Effect.tx` and is a one-operation
transaction (`vendor/effect-4.0.0-rc.112/src/TxRef.ts:225-242`, `:241`, `:334-337`, `:368`,
`:460-463`).

**T3. The boundary.** `tx(e)` reads the fiber's context. If a `Transaction` is already there,
`tx(e)` is just `e`: nesting is flat, with no inner boundary and no partial rollback. Otherwise
it makes a fresh record and runs a loop under `uninterruptibleMask`. Each round runs `restore(e)`
with the record provided as the service. If that fails and the flag is set, it first waits
(T6). Then it captures the exit and decides (T4)
(`vendor/effect-4.0.0-rc.112/src/Effect.ts:24274-24311`).

**T4. The decision.** The loop's `step` is one synchronous block, so nothing runs in its middle.
If the retry flag is set, or some journaled cell's version differs from its entry (T5), it clears
the record (flag false, journal empty) and runs the body again. Otherwise it commits (T7) on a
success and answers the exit, or clears the record and fails with the cause on a failure
(`vendor/effect-4.0.0-rc.112/src/Effect.ts:24296-24306`, `:24356-24359`). So a failure is
reported only after its reads are validated; a failing attempt with stale reads runs again. A
failing transaction commits nothing.

**T5. Validation.** Each journaled cell's current version must equal its entry's version. The
versions are per cell: there is no global clock and no lock
(`vendor/effect-4.0.0-rc.112/src/Effect.ts:24313-24320`). A value changed and changed back
still counts as a conflict, because the version moved.

**T6. Retry.** `txRetry` sets the flag and fails with `Cause.interrupt(own fiber id)`
(`vendor/effect-4.0.0-rc.112/src/Effect.ts:24397-24403`; `interrupt` is
`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:4299`).

- (a) The failure passes through the body's handlers like any interrupt. `onExit` finalizers
  see an interrupt exit. `catchCause`, `matchCause`, `exit` and `ignoreCause` catch it.
  `catchIf` does not, because its test reads the first `Fail` reason and an interrupt has none
  (`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:157-165`, `:2803-2805`).
- (b) Catching it does not cancel the retry: the flag stays set. The wait (c) runs only when the
  body's exit is a failure (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24289-24292`). If the body
  swallowed the retry and succeeded, T4 runs it again at once, with no wait (`:24297`). If nothing
  changes, this repeats without end, broken only when the run loop yields to other fibers.
- (c) The wait, `awaitPendingTransaction`
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24322-24341`), takes the journal's cells at that
  moment, which is every accessed cell, read or written. It registers one wake callback under a
  fresh key on each and parks. The callback removes the key from all those cells, then resumes
  the fiber with `void`. An interrupt while parked runs the same removal (the callback's cancel,
  `:24339`). With no accessed cell, the fiber parks with nothing that can wake it.
- (d) The wait runs *before* T4's validation: it sits inside the body chain (`:24289-24293`),
  and validation sits in `step` (`:24297`). An attempt whose reads were already made stale by
  another commit therefore parks on cells whose change has already happened. If no later commit
  touches those cells, it never wakes, although a re-run would proceed. This is a lost wakeup
  (inferred; not reproduced). Harris et al. validate before waiting (§6.3 of the paper), and so
  does ZIO (§1.5).

**T7. Commit.** `commitTransaction` is one synchronous block
(`vendor/effect-4.0.0-rc.112/src/Effect.ts:24343-24354`). It walks the journal in first-access
order. For each entry whose value is not identical (`!==`) to the cell's value, it bumps the
version and writes the value. Then, **whether or not the cell changed**, it schedules every
pending callback of the cell as a task on the *committing* fiber's dispatcher at priority 0, in
registration order, and empties the cell's pending map.

- (a) Every successful transaction, a read-only one included, wakes every retry waiter of every
  cell it accessed. A bare `TxRef.get` outside any transaction is a one-operation transaction
  (T2), so it wakes them too.
- (b) The documentation says a retrying transaction waits until an accessed value *changes*
  (`vendor/effect-4.0.0-rc.112/src/TxRef.ts:32-35`;
  `vendor/effect-4.0.0-rc.112/src/Effect.ts:24366`). The code wakes it on any committed
  *access*. This note follows the code.
- (c) The woken fiber runs when the host fires the committer's dispatcher
  (`vendor/effect-4.0.0-rc.112/src/Scheduler.ts:207-233`). The task removes the waiter from all
  its cells, then resumes it (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24332-24334`). If the
  waiter got two tasks, from two commits before the first task ran, the second one resumes
  nothing, because of the `resumed` flag
  (`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:1117-1119`). A resume evaluates the
  fiber at once, inside the task (`:1120-1121`).
- (d) The journal is not cleared after a commit (`:24300-24305`). That is visible only through
  a forked child (T10).

**T8. Interruption.** The loop is uninterruptible except inside `restore`. The body and the
wait can be interrupted if and only if the fiber was interruptible when `tx` began
(`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:4340-4352`). Validation and commit are
never interrupted. An interrupted body or wait exits with the interrupt. T4 then either reports
it, or clears and runs again, and that re-run fails at once because the pending interrupt fires
as `restore` re-enables interruption (`:4324-4328`). Either way nothing commits and the body does
not run a second time (inferred).

**T9. Preemption.** The body is ordinary code on the run loop. rc.112 may yield before any
operation once the op count reaches `MaxOpsBeforeYield` (default 2048), or whenever a custom
scheduler says so, unless `PreventSchedulerYield` is set
(`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:643-652`;
`vendor/effect-4.0.0-rc.112/src/Scheduler.ts:174-176`, `:269-272`, `:295-298`). A yield can also
fall between the body's end and `step`, because delivering the exit is one more run-loop
iteration (`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:3621-3637`, `:4624-4645`). Other
fibers also run at a park inside the body, and when the body completes a `Deferred` that has a
parked waiter, because the waiter is evaluated inside the completing call (`:1117-1124`).

The body may contain any effect. rc.112's own `txRetry` example completes a `Deferred` inside
the body (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24381-24388`). Effects other than `TxRef`
writes are neither undone nor deduplicated: they happen once per attempt. The consequences of
preemption are conflicts (a T4 re-run), stale reads by an attempt that will be thrown away,
and T6(d).

**T10. Fibers.** A fiber forked inside a body inherits the parent's context
(`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:5273`). Its `TxRef` operations therefore see
the parent's `Transaction` (T3) and write the parent's journal, and its `txRetry` sets the
parent's flag and fails the child. After the parent commits, the child's accesses go to a journal
that nobody will commit (T7(d)) (inferred).

**T11. The rest.** User code can provide its own record with `provideService(Transaction, …)`,
as the service's doc example does (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24201-24205`).
`TxRef` writes under such a record are never committed. An allocation made by an attempt that
fails or retries is kept (T1), as in Harris et al. §3.5.

## 2. The designs, tested against rc.112

### 2.0 What "the same observable semantics" can mean

The theorems compare `Obs`, which is every fiber's exit and the stores, without the trace
(`src/Effect4/Laws/Machine/Behaviour.lean:28-31`, `:48-49`). A design can match rc.112 in two
strengths:

- **Lockstep.** For every decision tape, it reaches the same `Obs` as rc.112 under the same host
  choices. This is what the truth harness checks. It needs the same operation count, because the
  op budget decides where yields fall.
- **Same outcomes.** Every `Obs` the machine reaches under some tape, rc.112 reaches under some
  tape (soundness), and the other way round (completeness).

### 2.1 "A straight body runs atomically in one machine step": not today, but true after two small changes

As the machine stands, a body in the straight fragment does not run atomically, for two reasons.

- The machine runs a body one primitive at a time and may inject a yield before any of them,
  either when the op budget is reached or when the tape says so
  (`src/Effect4/Machine/Fibers.lean:1005-1020`, `:444-445`, `:2064-2065`). The straight
  fragment's own theorem says this in passing: `run_eq_meaning` holds "under the op budget or
  past it, where the root yields, parks, and `flush` fires"
  (`src/Effect4/Laws/Program/Agreement/Machine.lean:1892-1895`). That is harmless for one fiber
  and not for two.
- `Straight` admits the `Deferred` completion rows (`src/Effect4/Program/Fragment.lean:28-31`,
  `src/Effect4/Program/Native.lean:125-133`). A completion resumes its waiters inside the
  completing step (`src/Effect4/Machine/Stores.lean:1142-1152`, mode `now`;
  `src/Effect4/Machine/Fibers.lean:1115-1124`, `:1780-1787`), as rc.112 does
  (`vendor/effect-4.0.0-rc.112/src/internal/effect.ts:1117-1124`). So a straight body can run
  another fiber in its middle.

Two changes make the claim true.

1. **Prevent yields for the whole transaction.** The machine already implements rc.112's
   `PreventSchedulerYield`. It is a context reference whose value the fiber caches
   (`src/Effect4/Machine/ContextMap.lean:665-666`, `:699-702`;
   `src/Effect4/Machine/Stores.lean:82-89`; `RunFiber.preventYield`,
   `src/Effect4/Machine/Fibers.lean:241`), and `injectYield_prevented` proves that no yield is
   injected while it is set, tape verdicts included
   (`src/Effect4/Laws/Machine/Clauses.lean:111-115`).
2. **Admit only bodies that cannot park, fork or resume another fiber inline.** This is a fold
   over the body (§2.6).

With both in place, no command of another fiber runs between a transaction's first access and
its commit. This is inferred from the command loop (`src/Effect4/Machine/Fibers.lean:1795-1941`)
and its settle rules (`:1754-1775`): a fiber that neither parks, yields, forks nor owes a `now`
resume keeps the loop to itself, and tape decisions are taken only between command loops
(`:2058-2083`). It is the isolation lemma of §3. Three things follow.

- Every version check would pass, so versions carry no information and are dropped.
- There is no conflict re-run, no stale read and no lost wakeup.
- The journal keeps only two jobs. It holds the writes until commit, so that a retry or a
  failure can drop them. And it remembers which cells were accessed, for the wait set and the
  wake set. Only one transaction can be open at a time, so one record in the store does both.

**Fidelity.** This is rc.112 running each transaction under `PreventSchedulerYield`, for
admitted bodies. It is lockstep with that configuration if the rows and the wrapper compile to
rc.112's primitive structure, as the tree does for other combinators.

Against plain rc.112 it has the same outcomes on every tape that never yields inside a
transaction. The runs it loses are exactly T9's consequences: extra attempts, stale reads by
doomed attempts, and T6(d). Extra attempts are visible only through non-`TxRef` effects and
allocations in the body, and through scheduling. For bodies whose only effects are `TxRef`
operations and pure computation, a preempted rc.112 run has the same outcome as a run in which
the transaction ran whole at its commit point. The committed attempt's reads were validated,
so each of them commutes with every step that ran between it and the commit. That is Lipton's
reduction as Flanagan and Qadeer's movers use it ("A type and effect system for atomicity",
PLDI 2003) (inferred). For such bodies, `Obs` loses only T6(d).

### 2.2 "Retry parks the fiber on the wake lists of the cells it read": yes, with three corrections

- **The wait set is every accessed cell, read or written,** because rc.112 keeps one journal
  (T2, T6(c); `vendor/effect-4.0.0-rc.112/src/Effect.ts:24325`, `:24336-24338`).
- **The wake goes to every waiter of every cell a committing transaction accessed, changed or
  not.** Wakes go out in first-access order, then registration order. Each is delivered as a
  scheduled resume on the committer's dispatcher at priority 0, one task per waiter
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24349-24352`). In this tree that is
  `WakeMode.scheduled committer 0` (`src/Effect4/Machine/Wake.lean:62-65`), which `drainOwed`
  posts as one `Task.resume` per owed resume (`src/Effect4/Machine/Fibers.lean:1780-1789`). It is
  **not** DB-13's coalescing batch (`WakeList.schedule`, `src/Effect4/Machine/Wake.lean:210-221`),
  which rc.112's STM does not do.
- **rc.112 removes the woken waiter from its other cells before it resumes it**
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24332-24334`). `Task.resume` cannot run a store step
  first. Either the removal becomes the resumed fiber's first operation, which is one more
  counted operation than rc.112, or `Task` gains a form that removes and then resumes, which is
  exact.

Everything else is already in the tree. Each cell's waiters form a `WakeList Unit`
(`src/Effect4/Machine/Wake.lean:119-123`). A retry registers the same `(fiber, token)` on each
list of its access set (`WakeList.register`, `:133-134`), and its cancel removes it from each
(`WakeList.cancel`, `:153-156`). That is a `Deferred` await over a list of cells rather than
one cell (`src/Effect4/Machine/Stores.lean:1120-1136`; the registration hook,
`src/Effect4/Machine/Fibers.lean:491-493`). Duplicate wakes for one waiter are inert under the
token guard, as rc.112's `resumed` flag makes them (`src/Effect4/Machine/Fibers.lean:1814-1827`;
`drive_resume_wrong_token`, `src/Effect4/Laws/Machine/Clauses.lean:452`). The `WakeMode` and
`Task` docstrings already list the STM pending wake as a scheduled-resume site
(`src/Effect4/Machine/Wake.lean:57-61`, `src/Effect4/Machine/Fibers.lean:108-114`).

No store produces a scheduled owed resume today. The timer resumes `now`
(`src/Effect4/Machine/Timer.lean:18-27`), and the scheduled arm of `drainOwed` is reached only in
proofs (`src/Effect4/Laws/Machine/Book.lean:565`, `src/Effect4/Laws/Machine/Handles.lean:647`).
So the commit would be that arm's first producer. `Task.wake` is in the same position: DB-13
notes that it has no rc.112 producer yet (`SCHED-FB-PRODUCER`, `docs/DESIGN-BASIS.md:529-532`).

This keeps DB-13's ruling that "`TxRef` is its own subcalculus, not a policy on this list"
(`docs/DESIGN-BASIS.md:532`). The transaction stays its own subcalculus, and only its wait uses
lists.

### 2.3 Read and write sets: static footprint or dynamic set

The semantics needs the dynamic set; everything around the semantics can use the static one.
Here a *footprint* means the set of cells a transaction may touch, as a fold over its body
computes it.

The dynamic access set is exact and costs nothing: the open record collects it as the body
runs, and it is the set of rc.112's journal keys (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24325`).
A static footprint over-approximates it. It counts both arms of a `select` and of a handler, and
it can only name cells by terms or allocation sites, because handles are values. Used as the
wait set or the wake set, it adds wakes rc.112 does not perform. That means more dispatcher
tasks and more runs of a body, which shows in scheduling and in any non-`TxRef` effect of the
body, so lockstep breaks.

What the static side is right for:

- **Admission.** The fragment of §2.1 is a Boolean fold by exclusion, as `Straight` is
  (`src/Effect4/Program/Fragment.lean:18-50`).
- **Refusing a retry that a handler swallows** (T6(b)). Nothing else can run inside the
  transaction, so the immediate re-run would repeat until fuel runs out.
- **Refusing `txRetry` outside any `tx`.** rc.112 refuses it by type: `txRetry` requires
  `Transaction` (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24397`). Here it is a lexical check.
- **Flattening nested `tx`.** This is exact after expansion, because `Eff` has no function
  abstraction, so all nesting is lexical. rc.112 decides nesting at run time through the context
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24275`).
- **Specialisation.** A `tx` whose body is one `TxRef` row is one store step plus its commit's
  wakes. rc.112's bare `TxRef` operations are exactly such one-operation transactions
  (`vendor/effect-4.0.0-rc.112/src/TxRef.ts:241`).
- **Proofs.** The frame fact (a transaction changes only its footprint's cells and whatever
  other rows it performs), and commutation of transactions with disjoint footprints.

### 2.4 When a journal is needed

A journal is needed exactly when another fiber can run between a transaction's first access and
its commit (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24297`, `:24313-24320` decide what happens
then). That occurs in four cases:

1. the body parks: the asynchronous rows, `awaitFiber`, `yieldNow`, the external rows, and the
   await and race actions;
2. the body forks: in rc.112 the child shares the journal (T10);
3. the body resumes another fiber inline: the `Deferred` completion rows, and the interrupt
   actions, which evaluate an idle target at once (`src/Effect4/Machine/Fibers.lean:1323-1326`);
4. the scheduler preempts the body, which preventing yields rules out.

For cases 1–3 the choice is to refuse the body, or to add rc.112's journal with versions
(design A below). rc.112's own `txRetry` example falls under case 3: it completes a `Deferred`
inside the body (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24384`). A fold cannot know that the
`Deferred` has no waiter yet, so it refuses the example.

### 2.5 Four designs

**A. Copy rc.112 step for step.**

- *What it adds.* A `TxRef` store whose cells hold a value, a version and a waiter list. A
  journal store, reached through a handle held in the context as the `Transaction` service, so
  that a forked child behaves as in T10. rc.112's wrapper as compiled code: the context test for
  nesting, `uninterruptibleMask`, the loop, the service region, the handler that waits on retry,
  the exit capture, and a store step that either validates and commits or clears. `txRetry` as a
  flag write plus the interrupt failure. The retry park on several lists, and the per-waiter
  scheduled wake. Loops here have a pure step (`iterate`, `src/Effect4/Program/Eff.lean:326-336`),
  so the commit becomes a row that runs after the exit capture: one more operation per round than
  rc.112's `step`, unless the count is adjusted.
- *Fidelity.* Lockstep with rc.112 under every tape, including stale reads, T6(d), the extra
  runs, and the fork case unless it is refused.
- *Machinery.* Two stores, a handle kind for the journal, about six rows (make, access through
  the journal, validate-and-commit-or-clear, set the flag, the registration and its cancel), and
  the conflict path.
- *Proof cost.* The typed state needs columns for the cell values and the journal entries (both
  typed by one cell table), the journal handle sort in `HandlesFit`, and the flag. The wrapper's
  control goes through S2's existing arms: masks, the loop, catch and exit. Nothing of the
  straight fragment's meaning carries over, because the wrapper has masks and a loop.

**B. Atomic transactions on the run loop (recommended).**

- *What it adds.* A `TxRef` store whose cells hold a value and a waiter list. One
  open-transaction record: the write buffer, the accessed cells and the retry flag. `tx`
  compiled as rc.112's wrapper without the conflict path, with yields prevented. The admission
  fold. A runtime guard: a fiber that parks, yields or forks while the record is open stops the
  machine with a named frontier (as `Stuck` does, `src/Effect4/Machine/Fibers.lean:386-393`), so
  a mistake in the fold shows as a frontier and never silently. The retry park and wake are as
  in A.
- *Fidelity.* Lockstep with rc.112 running each `tx` under `PreventSchedulerYield`, for admitted
  bodies, if the rows and wrapper keep rc.112's operation count. Against plain rc.112, the same
  outcomes on every tape that never yields inside a transaction. Bodies outside the fragment are
  refused.
- *Machinery.* One store, one record, four or five rows, the fold and the guard. There are no
  versions, no journal handle and no conflict path.
- *Proof cost.* The cell column (a table like `HeapNat`), the record's buffered values typed by
  the same column, and the park answering `unit`. Beyond those, one isolation lemma, and a
  meaning theorem for a transaction stated against C's handler.

**C. One step through the meaning.**

- *What it adds.* The whole transaction is one machine operation. The machine computes the
  body's meaning with the straight fragment's denotation
  (`src/Effect4/Laws/Program/Denote.lean:66-131`), under a handler that buffers `TxRef` writes,
  then commits, discards or parks.
- *Fidelity.* The same outcomes as B, but not lockstep. A transaction counts as one operation
  where rc.112 counts many, unless the machine charges the count the compiled body would have
  taken along its path. Trace events inside the body vanish, which is harmless, since the trace
  is not in `Obs`.
- *Machinery.* The least state: no record in the machine at all. But it puts an evaluator for
  the fragment inside the runtime. `denote`, `storeHandler` and the `Effects` free monad would
  move from the Laws layer into the runtime's import closure, and with them into the LCNF cut
  and the generated OCaml engine.
- *Proof cost.* The lowest. The transaction's meaning is the existing straight meaning under a
  different handler, and `run_eq_meaning`
  (`src/Effect4/Laws/Program/Agreement/Machine.lean:1896-1913`) is the pattern for relating it
  to the run loop.

**D. Library code over `Ref` and `Deferred`, with no new store.** This does not work, for three
reasons.

- A `Deferred` completion resumes its waiters inline
  (`src/Effect4/Machine/Stores.lean:1150-1152`), while rc.112's commit posts one task per waiter
  on the committer's dispatcher (T7). The woken fiber would run inside the committer's step
  instead of when the host fires the dispatcher.
- A commit over several cells would be several separate steps, unless a new row writes them
  together.
- The value language cannot hold a journal today.

It is not expressible now. Once it is, it will still schedule wakes differently.

**Ranking.**

| | first | second | third | fourth |
| --- | --- | --- | --- | --- |
| (i) fidelity to rc.112 | A | B | C | D |
| (ii) new trusted machinery, least first | B: one store and one record, all run by the existing loop; the guard backs the fold | C: less state, but a second evaluator in the runtime | A: two stores, a handle kind, versions, the conflict path | D adds nothing and fails |
| (iii) proof cost, least first | C | B: C's cost plus the isolation lemma | A | — |

### 2.6 The fragment

The fold `TxBody` works by exclusion and names every constructor, as `Straight` does, so a new
`Eff` constructor is a missing case until someone classifies it.

**Admitted:**

- `succeed`, `fail`, `failCause`, `sync`, `suspend`, `bind`, `select`, `exit`, `catchCause`,
  `matchCause`, `onExit` and `catchIf`;
- `perform` of a `.sync` row, except the rows that resume another fiber inline
  (`deferredSucceed`, `deferredFail`);
- the `TxRef` rows;
- `txRetry`, except under `catchCause`, `matchCause` or `exit` in the same transaction;
- a nested `tx`, which is flattened;
- `service`, and `provideService` except rebinding the two scheduler references;
- `withFiber` reading the fiber id.

**Refused:**

- the asynchronous rows (`deferredAwait`, `sleep`, external);
- `yieldNow` and `awaitFiber`;
- every other `withFiber` action (fork, interrupt, await, race, `setContext`, close);
- `scoped`, `acquireRelease` and `provideLayer`.

`iterate` and `gen` never park by themselves, so the run loop can execute them inside a
transaction. The meaning theorem covers them once their meanings are stated; the budgeted meaning
already exists for `iterate` (`meaningB`, `src/Effect4/Laws/Program/DenoteB.lean:241`). A loop
that never ends inside a transaction reaches a fuel frontier, where rc.112 under
`PreventSchedulerYield` would hang.

This fragment covers every transaction body of the ten modules (§1.4), apart from
`TxHashMap.flatMap` with a caller effect outside it.

## 3. The recommendation, and what it needs from the tree

**Recommendation.** Use design B at run time, with design C's handler as its specification in the
Laws layer. Use design A only if the owner wants transaction bodies that park (§5, Q3). Land it
after S3 of the typed-state milestone, and after R1 of the map note (stores hold data, never
code), so the new store holds data from the start.

**What has to exist.** Each item is new data or a new row on existing machinery.

1. **A handle sort and a store.**
   - Append `txRef` to `HandleKind` (`src/Effect4/Machine/Value.lean:57-66`; its bytes are only
     ever appended, never renumbered).
   - A store with `cells : List TxCell`, where a `TxCell` is a value and a `WakeList Unit`.
   - `open : Option TxOpen`, where a `TxOpen` is the owner fiber, the buffer
     (`List (TxRefKey × Val)`), the accessed cells and the retry flag.
   - The owed resumes a commit produces, as data (R1 of the map note).
   - Add the store to `Stores` (`src/Effect4/Machine/Stores.lean:1719-1733`). There is no
     version field.
2. **Rows,** at `number` first, as `Ref` is:
   - `txMake`;
   - `txAccess cell f`: T2's `modify` through the open record, with `get`, `set`, `update` and
     `modify` as named functions the way the `Ref` rows have them
     (`src/Effect4/Machine/Stores.lean:880-917`);
   - `txOpen`;
   - `txClose exit`. On a success it applies the buffer, owes a scheduled resume at priority 0
     on the owner's dispatcher to every waiter of every accessed cell, and closes the record. On
     a failure it discards the buffer. On a retry it discards the buffer and answers the accessed
     cells;
   - `txRetry`, which sets the flag. Its compile follows the flag write with T6's interrupt
     failure, using the fiber id, so the body's handlers see what they see in rc.112.

   Outside a transaction, a `TxRef` row is `tx` of that row (T2).
3. **The retry park.** A registration name over a list of cells, with its cancel name,
   mirroring `registerAwait` and `cancelAwait` (`src/Effect4/Machine/Stores.lean:1826-1829`,
   `:1891-1893`; `RunInterp.registerAsync`, `src/Effect4/Machine/Fibers.lean:491-493`). It
   answers `void`. It also needs a `Task` form that removes the woken waiter from its other
   cells and then resumes it (§2.2).
4. **`Eff.tx body`, a scoped constructor like `uninterruptible`.** The literature review
   classed `TxRef.transaction` as scoped (`docs/research/2026-09-07-lit-papers.md:110-111`), and
   the grill ruled "constructors for the scoped set"
   (`docs/research/2026-09-07-grill-agenda.md:21`). Its compile does four things:
   - prevent yields for its duration, through the existing `provideService` region on
     `preventYieldKey` or by setting the fiber's cached flag directly;
   - open the record, run the body, and close the record;
   - on a retry, park on the answered cells and go round again;
   - make the body and the park interruptible exactly as T8 says.

   It prints as `Effect.tx(…)`, `Effect.txRetry` and `TxRef.*`, and reads back the same. The
   generated fold and lenses, the wire tag and the arms table follow from the constructor
   (`src/Effect4/Program/Fold.lean:1-4`, `src/Effect4/Program/Eff.lean:486-521`).
5. **The fold `TxBody`** (§2.6), beside `Straight` in `src/Effect4/Program/Fragment.lean`. The
   checker refuses a `tx` whose body fails the fold, citing the rc.112 lines in the refusal row.
6. **The runtime guard.** A new `Stuck` reason for a park, yield or fork while the record is
   open (DB-04: a frontier must be visible).
7. **The checker.**
   - `tx body` has the body's type.
   - `txRetry` has answer `never` and error `never`, as in rc.112
     (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24397`).
   - The `TxRef` rows get `Row` entries, as the `Ref` rows have
     (`src/Effect4/Program/Native.lean:154-221`).
8. **Refusal rows and design issues, each citing its rc.112 lines.**
   - No preemption inside a transaction (T9).
   - Bodies outside the fragment, including rc.112's own `txRetry` example (§2.4).
   - A retry swallowed by a handler (T6(b)).
   - Direct use of the `Transaction` service (T11).
   - A fork inside a body (T10).
   - One finding to record: T6(d), and the documentation-versus-code difference of T7(b).

**What the typed-state invariant needs.** This comes after the milestone, as a refinement the
composed graph already anticipates
(`docs/research/2026-09-18-typed-state-composed-graph.md:232-249`).

- A cell table in the world beside `Ρ` and `Π`, at `number` in the first cut. It is the twin of
  `HeapNat` (`src/Effect4/Laws/Program/Progress.lean:72`), and `txMake` extends it.
- The open record's buffered values, typed by the same table. The position census will list
  `TxCell.value` and `TxOpen.buffer`. The accessed-cell list, the flag and the waiter lists hold
  no values.
- The park-handshake invariant the map note asks to state (its §2.1), extended to one token
  registered on several lists.
- `OpOk` and `AnswerOk` rows. The retry park answers `unit`, as a sleep does (composed graph,
  `:214-215`). The commit's owed resumes carry `success unit` and are delivered through the
  existing `drainOwed` site (composed graph, `:105`).
- S1: one arm for `tx`, whose body the checker types and whose denotation is a store program
  between `txOpen` and `txClose`, plus the park. The rows' store clauses extend `progress` and
  `answer_typed`.
- `HandlesFit`: the `txRef` handle sort.

Two lemmas are about isolation and meaning rather than typing, and they are the substance. The
isolation lemma: under prevented yields and `TxBody`, no command of another fiber runs while the
record is open. Its corollary is that at most one record is open at a time. The transaction
meaning theorem: the run from `txOpen` to `txClose` computes the straight meaning of the body
under the buffering handler. That is `run_eq_meaning`'s shape, applied to part of a run.

**What not to add.** Versions, a journal handle in the context, a conflict path, a second
scheduler, a coalescing batch for these wakes, and a store for any of the ten modules.

## 4. The general lesson for composed abstractions

**4.1 When a composed abstraction needs its own rows.** STM and its modules suggest a test.
Call a *synchronous block* the code rc.112 runs between two run-loop operations. An abstraction
is library code over its base primitives when two things hold:

- each of its synchronous blocks touches state that one base row already updates in one step;
- each of its waits uses a wake the base already has: the same waiters, the same delivery mode,
  the same dispatcher.

`TxRef` fails both tests, so it needs rows. Its commit writes many cells in one synchronous block
(T7), and its wake is a scheduled broadcast on the committer's dispatcher, which neither `Ref`
nor `Deferred` has. The ten modules pass both tests relative to `TxRef`, because every one of
their operations is a transaction over `TxRef` cells, so they are library code. This agrees
with the manifest review's advice for the derived `Ref` families: "prefer programs over existing
stores" (`docs/research/2026-09-07-manifest-review.md:335`).

**4.2 Keep a composed abstraction composed, because its footprint is observable.** In rc.112,
the cells an operation touches decide which fibers a commit wakes (T7(a)). So the representation
is part of the behaviour. `TxQueue.size` reads the queue's cells, so it wakes every blocked
`take`. A dedicated queue store with a one-waiter wake would wake one taker, and would not wake
anyone on `size`. A specialised store for a composed abstraction is faithful only if every
operation touches the same cells as the library code. Both sides are data here, so a fold can
check this: compute each operation's footprint on each side and compare.

**4.3 What static analysis of `Eff` buys here.**

- **Admission by a fold, not by a type.** rc.112's type says only that a body needs the service:
  `txRetry` has type `Effect<never, never, Transaction>`, and `tx` removes the requirement
  (`vendor/effect-4.0.0-rc.112/src/Effect.ts:24397`, `:24273`). Haskell's `STM` type restricts a
  body to transactional actions and pure code (Harris et al. §3.1). A fold over the data gives
  the same guarantee without a new monad or type index, and it can be finer: it can admit a
  `Ref` write and refuse a `Deferred` completion. The precedent is `Straight`.
- **Footprints for proofs.** A footprint, meaning the rows and handle terms a program may touch,
  gives the frame fact (what the program cannot change) and commutation (programs with disjoint
  footprints commute). The composed graph's advice to "factor the step by what a transition
  touches" (`docs/research/2026-09-18-typed-state-composed-graph.md:61-65`) is the same idea,
  applied to scheduler steps.
- **Specialisation.** A transaction whose footprint is one cell and whose body is one row is one
  store step. Library code has no function abstraction after expansion, so it can be partially
  evaluated.
- **Exact scoping checks.** Flattening nested `tx`, finding `txRetry` outside a transaction, and
  finding a retry swallowed by a handler are all lexical after expansion.
- **Deciding library code or store** (4.1) mechanically. A fold over a library program's
  expansion can list its synchronous blocks together with their footprints.

**4.4 Where static analysis does not help.**

- **Aliasing.** Handles are values, so a fold sees terms or allocation sites, never cells. Lock
  inference for atomic sections has the same limit and pays for it with coarse locks (McCloskey
  et al., "Autolocker", POPL 2006; Hicks, Foster and Pratikakis, "Lock inference for atomic
  sections", TRANSACT 2006; Cherem, Chilimbi and Gulwani, "Inferring locks for atomic sections",
  PLDI 2008).
- **Sets the semantics defines at run time.** The retry wait set and the commit's wake set are
  rc.112's dynamic journal. A static over-approximation adds wakes (§2.3).
- **Scheduling.** Operation counts, yields, wake order and which dispatcher delivers a wake
  belong to a run under a tape, not to the program text.
- **Other fibers.** One program's footprint says nothing about what other fibers touch. "This
  transaction never conflicts" is a whole-program fact, and design B makes it unnecessary.
- **Foreign rows and loops that depend on data.** The first are opaque; the second may be
  unbounded.
- **Commutativity above the cell.** rc.112's collections keep a whole map in one cell, so any two
  operations on one `TxHashMap` touch the same cell. Transactional boosting replaces read and
  write sets with the object's own commutativity and abstract locks (Herlihy and Koskinen,
  PPoPP 2008). That would change wake sets, so here it would be a deviation from rc.112, not an
  optimisation.

**4.5 The effect type and the data are different levers.** The type records what a program
requires (`Transaction` in `R`). The data records the program's control shape and its footprint.
In this case every admission decision above is a fold, and none is a type, which supports the
owner's view.

## 5. Open questions for the owner

1. **Semantics: atomic (B) or preemptible (A)?** *Recommendation: atomic.* Register the deviation
   (no preemption inside a transaction; T9's extra runs and stale reads and T6(d) cannot happen)
   as a design issue with the rc.112 lines. Print `tx` as `Effect.tx(…)`. The harness then
   agrees in lockstep except when rc.112's op budget falls inside a transaction body; one pinned
   fixture should show that case.
2. **Mechanism: B (run loop and one record) or C (one step through the meaning)?**
   *Recommendation: B at run time, with C's handler as the Laws-level specification.* This keeps
   the runtime to one evaluator and keeps the proofs on the straight meaning.
3. **Bodies outside the fragment, including rc.112's own `txRetry` example: refuse them, or add
   A's journal for them?** *Recommendation: refuse, with named refusal rows, in the first cut.*
   Every transaction body of the ten modules is inside the fragment (§1.4). A's journal can be
   added later for these bodies without changing B.
4. **rc.112's wake-on-access (T7(a), T7(b)) and lost wakeup (T6(d)).** *Recommendation: copy
   wake-on-access exactly.* It is cheap, and it is what the code does, whatever the docs say. The
   lost wakeup cannot happen under B. Record it as an rc.112 finding, and reproduce it in the
   truth harness before anyone reports it upstream.
5. **A retry swallowed by a handler (T6(b)): refuse statically, or copy the immediate re-run?**
   *Recommendation: refuse.* Under B nothing else can run inside the transaction, so the copied
   re-run loops until fuel runs out. rc.112 under `PreventSchedulerYield` would hang the same way.
6. **Removing the woken waiter from its other cells (§2.2): a new `Task` form (exact), or removal
   as the woken fiber's first operation (one extra counted operation)?** *Recommendation: the new
   `Task` form.* The scheduler surface already adds task shapes by rc.112 site, and this site is
   listed there (`src/Effect4/Machine/Fibers.lean:108-114`).
7. **Where the open-transaction record lives: in the new store, on the fiber, or behind a context
   handle as rc.112 keeps it?** *Recommendation: in the store.* That keeps `RunFiber` a
   transcription of `FiberImpl`. A context handle matters only for the fork case, which is
   refused.
8. **Order.** *Recommendation:*
   - after S3 of the typed-state milestone and after R1 of the map note;
   - `TxRef` at `number`, with `tx` and `txRetry`, as the first vertical slice;
   - the modules after cells can hold options, lists, maps and handles, a precondition Queue and
     PubSub share.
9. **Two wording amendments.** *Recommendation:* point the map note's §8 item 5 at this note; STM
   needs a store family plus one record, not a new kind of state. Refine DB-13's sentence
   (`docs/DESIGN-BASIS.md:532`) to: "the transaction is its own subcalculus; its retry wait is a
   broadcast on per-cell waiter lists, delivered as scheduled resumes on the committer's
   dispatcher."
