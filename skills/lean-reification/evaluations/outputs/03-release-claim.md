# Release-claim review

The release note is not supported. Its equivalence and unconditional completion claims are contradicted by the supplied examples. Full coverage of the language and compliance with the proof policy remain unverified.

## Supported release wording

“The supplied model theorem establishes that every source trace has at least one equal trace in the target model. A host harness also matched the source model on 60 selected finite inputs under one scheduler. These results do not establish equality of the two sets of possible traces, coverage of every language case, or eventual completion of every request.”

The first sentence describes the supplied theorem's direction and universal source-run scope. The second describes the supplied finite host observations. Neither is a claim that this review ran Lean, inspected a saved proof, or reran the harness. Acceptance of the theorem under the project's dependency policy remains a separate open question.

## Review boundary and required connections

The reviewed artifact is the release note and the six evidence entries supplied in Case 03. The observation is the full trace, including the difference between returning a value and failing. No source revision, theorem declaration name, executable bytes, toolchain pin, or runtime version was supplied. These are a closed paper exercise's limits, not requests to inspect the real repository.

## Prioritized findings and next evidence

1. **Release blocker: the target has an observable behavior the source forbids.** Class: representation/semantic defect in the claimed equivalence. For P, the source trace set is exactly {“read, return 1”}; the target permits both “read, return 1” and “read, fail.” Therefore “read, fail” belongs to the target set but not the source set. The supplied theorem proves that the source set is included in the target set, which is consistent with this defect; it does not prove the reverse inclusion. This is a decisive counterexample, not an absence of testing. **Smallest next step:** use the supported narrower wording now. To retain an equivalence claim, the semantic contract and target owners must first resolve the extra failure through an authorized change, then provide the reverse-inclusion theorem for all permitted target traces, alongside the existing direction and their applicable trust receipts. More examples cannot establish equality for the supplied unequal sets.

2. **Release blocker: a permitted schedule can starve a ready request forever.** Class: semantic defect in the progress claim, with an unstated external assumption. The evidence expressly allows the scheduler to leave a ready request unselected forever. That allowed execution contradicts “every pending request eventually finishes.” Sixty terminating selected executions cannot rule it out. **Smallest next step:** remove unconditional progress from this release claim. For a replacement conditional claim, the scheduling/semantic contract owner must state the exact fairness and environment assumptions, prove the desired eventual-completion property under those assumptions, and identify how the intended runtime satisfies them. Fair selection alone does not establish that a selected computation or an unanswered external operation can finish; those obligations must be stated rather than silently assumed.

3. **Trust acceptance blocker: malformed source was silently excluded.** Class: evidence failure. The source-trust scanner skipped one semantic module when parsing failed. Its result therefore leaves that module unexamined, even if other modules passed. This establishes an audit coverage defect; it does not establish a logical defect in the skipped module. **Smallest next evidence:** the trust-gate owner must show that the malformed-input case causes an explicit failed or inconclusive audit, and supply a processed-module/declaration census for a successful scan with no unreported omissions. Any intentional exclusion must narrow the acceptance claim. A proof dependency report is also needed for the claimed theorems; a source scan is not a substitute for it.

4. **Trust acceptance blocker: a renderer exception was expanded into permission for semantic declarations.** Class: evidence failure and policy mismatch. The only approved Classical.choice exception names the rendering declaration. Applying it to the entire module also excuses the new semantic admission theorem, contrary to the supplied policy. The exercise does not report that theorem's actual dependency list, so its individual compliance remains unverified; the exception's excessive scope is already established. **Smallest next evidence:** the trust-policy/gate owner must supply exact transitive dependency receipts for the renderer and admission theorem, restore the exception to the named renderer, and demonstrate that a semantic declaration depending on unapproved Classical.choice is rejected while the approved renderer passes. Permitted propext and Quot.sound dependencies should remain permitted. This finding does not require eliminating approved classical reasoning.

5. **Trust acceptance blocker: the unsafe self-test attributed the wrong failure to its detector.** Class: evidence failure. The planted case produced a nonzero exit because another module failed to build. There is no evidence that the unsafe detector was reached or rejected the planted declaration. **Smallest next evidence:** the build/gate owner must provide a successful baseline and an otherwise buildable planted unsafe case that both reach the detector, with the latter failing specifically on the planted declaration. The test should separately classify an earlier build failure as a failed prerequisite, not as successful unsafe detection. Keep the currently failing module outside any compiled-audit success claim until it is actually examined.

6. **Coverage blocker: the expected corpus repeats the generator's own blind spots.** Class: transformation gap. Both enumerate the same recursive-child table. A child omitted from that table can disappear from both outputs without disagreement. No actual omitted child was supplied, so full coverage is open rather than refuted. **Smallest next evidence:** the representation/generator owner must provide a pinned source export or recursive-field census produced independently of that table, and compare each required source construct and recursive field with its representation and generation case. Explicit exclusions belong in the claimed domain. An omitted-child challenge should then be caught by this independent comparison even if the generator and expected corpus share the omission.

7. **Execution-scope blocker: the host observations do not close the model-to-runtime connection.** Class: transformation gap and external boundary. The theorem relates model traces; the only reported host evidence is 60 selected finite inputs under one scheduler. No relation tying the generated artifacts to the modeled target, nor unrestricted-host correctness evidence, was supplied. **Smallest next evidence:** to make the finite host claim reproducible, the target/harness owner should record the exact generated artifacts, generator/source versions, runtime version, cases, decisions, observer, and results. For a broader generated-runtime claim, supply the required relation between source, generated artifacts, and target meaning, and name the remaining compiler/runtime assumptions. A larger finite corpus would still be finite evidence.

## Outcome and verification record

The current broad release sentence should not be accepted. The supported wording above can be used with its stated model, finite-test, and trust limits. Findings 1 and 2 establish false claims under the supplied semantics; findings 3–5 establish defects in the acceptance evidence; findings 6 and 7 identify required connections still open.

Verification performed here was a paper check of the two trace sets, the permitted starvation execution, theorem direction, test scope, and the supplied trust-policy facts. No Lean build, harness run, scanner, mutation test, source inspection, or dependency inspection was executed. No receipt has been invented. There are no repairs or successful rechecks to report.

No workflow ambiguity prevented this review. The exercise's prohibition on fresh execution controls the skills' usual inspection and verification steps; those steps remain explicitly unperformed. This document is an independent reading of the supplied evidence, not an independent check of compiled artifacts.
