# Case 06: choose the smallest assurance route

Use `$lean-reification-contract` and `$lean-reification-audit` to decide whether
these two records need additional work. This is a documentation exercise over
the supplied trusted receipts, not a request to run a new build or rewrite a
project's process.

The project uses the same graph-versus-leaf threshold described in this skill
pack. Existing authorization covers documentation only.

Record A is `PrintStyle`, a passive two-constructor label used to select visual
indentation. It has no admission, semantic, protocol, or cutover claim. Its exact
public signatures, two-case census, distinctness, spelling round trip, and
axiom report are already checked at the frozen revision. It is a standalone
leaf with one owner. The requested question is whether this leaf record is
complete. No runtime semantics, source retirement, or new behavior is claimed.

Record B is a new Boolean `allowed`, which decides whether an arbitrary raw
program may enter the checked language. The public type is tiny, and its two
output values are enumerated. The candidate function always returns false.
The promised profile must accept the documented one-operation valid program.
The only proof says that if `allowed` returns true, its input is well formed.
The author proposes treating B as a second passive leaf, complete after its
Boolean census.

For each, give the minimum justified verdict and necessary next action. Avoid
inventing global reification, liveness, host, or paper-instantiation obligations
for a record that makes no such claim.
