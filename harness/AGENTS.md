# Host-harness routing

This boundary contains TypeScript typechecking, Effect runtime and replay
vectors, language-service diagnostics, negative fixtures, mutations, and
coverage checks. Host evidence tests an exact target profile; it does not own
Effect4 semantics.

## Exact profiles

Every harness records the Effect package bytes, upstream revision,
TypeScript version, diagnostic-tool version, runtime, platform, and command it
exercised. Version-skewed language-service results are auxiliary evidence.
Direct checks against the pinned Effect runtime and TypeScript compiler remain
required.

Generated programs are inputs to independent typechecking and execution, not
self-validating evidence. Positive, negative, and mutation cases remain
separate. Runtime observations state their decision tape, scheduler inputs,
foreign registrations, and other ambient assumptions needed for replay.

## Routing results

Semantic counterexamples receive stable IDs in
`test/counterexamples/REGISTER.md`; their host fixtures live in the relevant
harness area and are linked from that row. Version- or profile-specific
refusals also enter the public surface ledger rather than creating duplicate
Effect4 carriers for missing host names.

Deterministic reports and coverage projections belong under `generated/` and
are regenerated by a recorded command. Caches, installed dependencies,
transient logs, and machine-specific paths are not canonical evidence.

A target proof-graph edge closes only when all evidence named by that edge is
present. A runtime pass cannot close a Lean simulation theorem, and a
diagnostic-tool pass cannot replace the direct target typecheck.
